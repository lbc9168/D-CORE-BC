## 文档与日志规则

文档分两类，职责严格分开，不得混写：

### docs/status —— 当前状态（快照 / 覆盖式）
- 只回答一个问题："现在每个模块是什么样、怎么运行的"，用现在时描述稳定状态。
- 固定只保留：overview.md（项目整体状态）、pipeline.md（端到端数据流 S01→S04）、每个核心模块/子项目各一份（按其 sNN 前缀命名，当前 s01a、s01b、s02a、s02b、s02c、s03、s04；新增模块如 s02e 同例），以及 external-tools.md（非流水线的独立小工具状态）。除此之外不在 status 里放其他类型文件。
- 每份模块状态文件用统一小节：① 职责（一句话）② 当前功能 ③ 如何运行（命令）④ 输入 / 输出（文件、表、JSON）⑤ 关键依赖与约束。
- 写法：覆盖式。状态变了就替换旧描述，绝不在这里追加历史；不写"我改了什么 / 为什么改 / 某次修复"（那是 changes），也不放 backlog / eval / review / 设计草案（归 docs/changes 或 docs/rules_and_plans）。

### docs/changes —— 变更日志（流水账 / 追加式）
- 只回答："发生了什么改动、为什么"，按时间组织，文件名 2026-Www.md（一周或一次 session 一份）。
- 追加式，不回头改旧条目。每条至少含：日期 · 涉及模块 · 做了什么 · 为什么 · 影响（动了哪些文件 / 表 / 接口）。

### 何时写（同步触发）
- 以"一个有意义的工作单元"为粒度（一次 session 收尾 / 一个功能或修复完成），不是每改一行。
- 收尾时：① 一定在 docs/changes 追加一条；② 仅当本次改动改变了某模块的当前功能 / 运行方式 / 输入输出契约时，才覆盖更新对应的 docs/status 文件。纯内部重构、不改变对外行为的修复，只记 changes，不动 status。

## 编程规则（v2 起生效，源自 coding_rules_draft）

1. 禁止 `except: pass` 或裸 `except: pass`；捕获异常必须指定具体类型，并用 `logging.error()` 记录信息与上下文。唯一允许沉默的情况是已知无害边界（如 ALTER TABLE 列已存在），且必须加注释说明。
2. 运行时输出统一用 `logging` 并写入文件（含时间戳/模块名/级别/内容）；`print()` 仅限脚本顶层入口的人机交互提示，关键节点可 print 但必须有 logging 备份。
3. 批量写库必须用事务包裹，禁止循环内逐条 `commit()`；单次写入超过 50 条用 `executemany()`。
4. 所有对外暴露的函数入口参数用 Pydantic `BaseModel` 校验（日期格式、数值范围、路径存在性）；非法参数在入口立即抛出，不得进入业务逻辑。
5. 所有 HTTP 响应必须检查 `status_code`：404 跳过不重试，429 等待≥30秒后重试，403 记录日志并终止，5xx 指数退避重试；未校验的响应禁止传入解析逻辑。
6. 所有从外部来源（JSON 文件、API 响应）加载的数据，进入业务逻辑前必须用 `zod` 或等效库做运行时结构校验，失败立即抛错。
7. 多线程共享的可变模块级变量必须用 `threading.Lock()` 保护，读写都在 `with lock:` 内完成。
8. `pipeline/flow.py` 每个阶段入口必须验证上一阶段输出（库文件存在、关键表非空、记录数合理），无效则主动抛带描述的异常。
9. API Key/凭据禁止出现在任何提交到 git 的文件；通过环境变量传入（本地 `.env`，CI 用 GitHub Secrets），`.env` 必在 `.gitignore`。

## 减少常见LLM编码错误的行为准则。可根据需要与项目特定指令合并。

**权衡：** 这些准则倾向于谨慎而非速度。对于简单任务，自行判断即可。

### 1. 先思考再写代码

**不要假设。不要隐藏困惑。把权衡摆到台面上。** 在动手实现之前：
- 明确说出你的假设。不确定就问。
- 如果存在多种理解方式，全部列出来——不要默默选一个。
- 如果有更简单的方案，说出来。该反驳就反驳。
- 如果有什么不清楚的，停下来。说明哪里让你困惑。提问。

### 2. 简洁优先

**用最少的代码解决问题。不写投机性代码。** - 不加超出需求的功能。
- 一次性代码不搞抽象。
- 没人要求的"灵活性"和"可配置性"不要加。
- 不要为不可能出现的场景写错误处理。
- 如果你写了200行但50行就能搞定，重写。
问自己一句："一个资深工程师会说这写复杂了吗？"如果是，简化。

### 3. 精准修改

**只动必须动的地方。只清理自己制造的问题。** 编辑已有代码时：
- 不要顺手"改进"旁边的代码、注释或格式。
- 没坏的东西不要重构。
- 匹配现有风格，即使你会用不同的写法。
- 如果注意到不相关的死代码，提一嘴就好——别删。
当你的修改产生了孤立代码时：
- 移除因你的改动而变成未使用的import、变量和函数。
- 不要动原本就存在的死代码，除非被明确要求。
检验标准：每一行改动都应该能直接追溯到用户的需求。

### 4. 目标驱动执行

**定义成功标准。循环验证直到确认通过。** 把任务转化为可验证的目标：
- "加验证"→"为非法输入写测试，然后让测试通过"
- "修这个bug"→"写一个能复现它的测试，然后让测试通过"
- "重构X"→"确保重构前后测试都能通过"
对于多步骤任务，列出简要计划：
1. [步骤]→验证：[检查项]
2. [步骤]→验证：[检查项]
3. [步骤]→验证：[检查项]
强成功标准让你能独立循环推进。弱标准（"让它能跑"）则需要不断澄清。

---

**这些准则起作用的标志是：** diff中不必要的改动更少了，因过度复杂化而返工更少了，澄清性问题出现在实现之前而不是犯错之后。
