# v2.1 P1 设计：提取多 agent 化（分阶段）+ 分类规则补全

> 创建：2026-05-24
> 性质：设计文档（spec）。经 brainstorming 与用户确认。实施计划另由 writing-plans 产出。
> 上游：[v2.1_plan.md](../../rules_and_plans/v2.1_plan.md) P1。**依赖 P0 评测集**（用于量化每次改动的进步/退步）。

## 目标（一句话）

把 s01b 一次性巨型 prompt 提取，重构为**分阶段、各自聚焦+校验**的提取链，并补全分类规则，系统性降低提取错误率（以 P0 字段级准确率度量）。

## 核心架构决策（已确认）

- **分阶段多次 LLM 调用**（不是 crewAI 真多 agent）：在重构后的提取器内按阶段顺序调用，每阶段一次聚焦调用 + 各自 guardrail 校验。crewAI crew 外壳保留为薄壳，重活在重构后的 `ProjectExtractorTool`（拆成 5 个阶段方法）。
- **LLM 供应商切换**：提取链默认改用 **deepseek-v4-lite**（从 Gemini 切换）。新增**配置化统一 LLM client 封装**（provider + model + key 配置一处），各阶段默认 deepseek-v4-lite、可单独覆盖。便于换源与 P0 A/B（Gemini vs DeepSeek）。
  - DeepSeek 走 OpenAI 兼容 API（新 client + base_url + `DEEPSEEK_API_KEY`，不入 git）；JSON 输出走 `response_format`。
  - ⚠️ 确切模型 id 与 SDK 以实施时环境实际可用为准（"deepseek-v4-lite" 按用户指定记录）。
- **成本门控**：Stage 1 相关性门先跑，**只有 valid 才进入 Stage 2-5**。
- s02a 去重 / s02b 归一化暂仍用 Gemini（混合供应商，本次不动；如需统一留待后续）。

## 阶段切分（已确认）

| 阶段 | 职责 | 输出字段 | 内置规则 |
|---|---|---|---|
| **S1 相关性 + 中企参与门** | 判 RE 相关性 + 是否有中企 | `status`(valid/no_chinese/irrelevant) + reasoning | **A.2 数据中心须 RE 供电才算**；非发电用电户（学校/医院/机场等）排除 |
| **S2 项目基本信息** | 名/国家/地点/分类/阶段/容量 | project_name(中)、country、location、**category**、project_stage、**capacity_mw**、storage_power_mw/energy_mwh | **A.1 垃圾发电/光热等分类映射**；**A.3 只有年发电量时反推装机容量**（按容量系数，标 capacity_source=derived） |
| **S3 金融信息** | 投融资 | total_investment_usd、financing_model、融资方、subcontract_amount、investment_date | 数值用 `bri_parse` 规范 |
| **S4 中方实体 + 参与方式** | 实体层级 + 参与 + 设备 | implementing_entity(+en)、subsidiary、involvement_type、**equipment_role/equipment_items** | **A.5 设备主/次细分**：按 `main_equipment.json`（项目类型→主要设备表）判主要/非主要设备 |
| **S5 摘要 + 自检** | 摘要 + 交叉校验 | project_summary | 基于 S1-S4 结构化结果自检（升级现有 Layer2 semantic_checks 思路） |

- 门控：S1 非 valid（no_chinese/irrelevant）→ 写 review.db，不进 S2-5。
- **枚举**全部经 `bri_enums` 注入 prompt + 校验（S1 成果，禁硬编码）。
- **chinese_unnamed**（未点名中企）属 P2（E.2），P1 的 status 仅 valid/no_chinese/irrelevant。

## 去硬编码：guardrail 枚举改读 bri_enums + 前端同步（P0.1 标注期发现，并入本期）

> 背景：P0.1 人工标注时新增了 involvement_type 枚举值 **"一体化方案提供商"（Integrated Solution Provider）**（设备供应商 + 同时负责设计/建造，现有几类概括不了；2026-05-25 加入 `enums_mapping.json`）。借此发现**多处仍硬编码枚举集合，违反 CLAUDE.md「枚举只改 enums_mapping.json、禁止在 .py/.ts 硬编码」硬规范**。本期一并清理（重构提取链时顺带做，零额外架构成本）。

- **`guardrails/format_checks.py`**：`VALID_CATEGORIES` / `VALID_PROJECT_STAGES` / `VALID_INVOLVEMENT_TYPES` / `VALID_FINANCING_MODELS` 四个集合**硬编码**，与 `enums_mapping.json` 会漂移（新值"一体化方案提供商"会被判「参与方式不合法」）。→ 改为从 `bri_enums`（`valid_categories()`/`valid_stages()`/`valid_involvement()`/`valid_financing()`）动态构建。
- **`guardrails/semantic_checks.py`**：`VALID_INVOLVEMENT_ENUMS` **硬编码**。→ 同样改读 `bri_enums.valid_involvement()`。
- **守护测试**：新增一致性测试，断言 guardrail 的合法集合 == `enums_mapping.json` 对应枚举键集，杜绝再漂移（现有 `tests/test_enums_consistency.py` 只校验 bri_enums↔json，未覆盖 guardrail）。
- **前端同步**：枚举改动后跑 `s04_web_visualization/scripts/copy-enums.mjs` 重新生成 `src/generated/enums.json`（前端读副本而非根文件）；`components/projects/ProjectDetail.tsx` 的 `ROLE_ZH_TO_EN` 硬编码英文 fallback → 优先用数据里的 `involvement_type_en`，避免新枚举值漏译。
- 注：纯 P0.1 评测/标注链**不受影响**（eval 走字符串比对、gold schema 不约束 involvement_type 取值），所以此项不阻塞当前标注，仅在重跑提取/重建前端前必须完成。

## 组件与文件结构

```
s01b_project_extractor/src/s01b_project_extractor/
├── tools/project_extractor_tool.py   # 重构：5 个阶段方法 + 编排；不再单巨型 prompt
├── llm/client.py                     # 新增：配置化统一 LLM client（provider/model/key）
├── prompts/                          # 新增：每阶段 prompt 模板（5 个，便于单独迭代）
│   ├── s1_relevance.py / s2_basic.py / s3_finance.py / s4_entity.py / s5_summary.py
├── guardrails/                       # 现有三层，改为每阶段输出后各自校验
└── knowledge/main_equipment.json     # 新增：项目类型→主要设备清单（A.5）
```

- **`main_equipment.json`**（A.5 知识表，新建）：如 `{"光伏":["组件","逆变器"],"风电":["风机/机组","叶片","塔筒","齿轮箱"],"水电":["水轮机","发电机"],"输变电建设":["变压器","GIS","换流阀"], ...}`。S4 据此判 equipment_role∈{主要设备,非主要设备,未提及}。
- **`llm/client.py`**：统一接口 `complete(prompt, *, stage, json=True) -> dict`；内部按配置选 provider（deepseek/gemini）；处理重试/退避/JSON 解析容错；模型名按 stage 可配置。

## 数据流

```
article ──► S1 relevance gate ──valid?──► S2 basic ──► S3 finance ──► S4 entity(+设备) ──► S5 summary/自检 ──► 合并为 extracted_projects 行
                 │ no_chinese/irrelevant
                 └──► review.db
每阶段：LLM client(deepseek-v4-lite) → JSON → 该阶段 guardrail 校验（失败重试/记录）
```

## 错误处理（遵 CLAUDE.md）

- 每阶段 JSON 解析/校验失败：按阶段重试 N 次；仍失败则该字段标缺失 + logging.error 记录上下文，不静默吞。
- LLM 调用失败：client 层指数退避；HTTP 状态码按规则处理。
- 阶段间：S1 门控失败/无输出 → 该篇进 review，不进后续。

## 测试策略

- **P0 评测是主度量**：重构后跑 `eval/run_eval.py`，逐字段对比重构前后准确率，**逐阶段验证是进步**（这是 P1 验收的核心证据）。
- `llm/client.py`：mock provider 单测（JSON 解析、重试、provider 切换）。
- 每阶段 prompt：用 P0 gold 子集做该阶段的定向回归。
- guardrail 每层单测保留；**新增 guardrail 合法集 ↔ enums_mapping.json 一致性测试**（去硬编码后守护，防再漂移）。

## 单一可信源/规则遵循

- 枚举注入与校验复用 `bri_enums`；数值解析复用 `bri_parse`；容量系数表（A.3）放配置/知识文件，不硬编码。
- API key 经 `.env`（`DEEPSEEK_API_KEY`），不入 git。

## 开放项（实施时定，非阻塞）
