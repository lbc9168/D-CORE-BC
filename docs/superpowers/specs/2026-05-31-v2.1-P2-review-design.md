# v2.1 P2 设计：复核机制（低置信二次核验 E.1 + 未点名中企 chinese_unnamed E.2）

> 创建：2026-05-31
> 性质：设计文档（spec）。经 brainstorming 与用户逐节确认。实施计划另由 writing-plans 产出。
> 上游：[v2.1_plan.md](../../rules_and_plans/v2.1_plan.md) P2。**依赖 P1**（分阶段提取链已投产，s01b 已拆 S1–S5 + llm/client + review.db）。
> 度量：复用 P0/P0.1 评测框架（`eval/`，97 篇金标准，P1 后基线 weighted ≈0.77）。

## 目标（一句话）

在 P1 分阶段提取之上加一层**复核**：① 用"确定性预筛 + 批判 agent"对可疑提取字段二次核验、能自动纠正的自动纠正、仍存疑的进人工清单（E.1）；② 给"明确有中企但未点名公司"的真实项目一个专属 `chinese_unnamed` 流，不再被误丢成 no_chinese / 糊成 Unknown（E.2）。

## 背景与依据（P1 现状）

- s01b 已分阶段：`prompts/`(s1–s5) + `stages/`(orchestrator + 各阶段 + entity_normalize) + `llm/client.py`（可配 DeepSeek/Gemini），crewAI 已移除。
- `review.db` 现有两表 `no_chinese_records` / `discarded_records`（S1 判 no_chinese/irrelevant 写入）。
- 置信度现状：只有 S5 corrections 带 confidence（≥0.8 采纳），**extracted_projects 无 per-field 置信度列**——E.1 因此不靠"模型自报置信度"。
- 当前 status 仅 3 值（valid/no_chinese/irrelevant）；`check-record.md` 记录痛点：有中企未点名被一律塞 Unknown，信息丢失。
- P1 后最弱项仍是 **entity（name_f1≈0.69 / role≈0.63）与 status（≈0.83，主要是过度收录）**——E.1 的批判 agent 直打这两项。

## 核心设计决策（brainstorming 确认）

1. **E.1 + E.2 同一份 P2 spec**，但两块解耦、可分开实现。
2. **E.1 = 自动纠正 + 人工兜底（两者结合）**：改字段值（低风险）自动；改"存不存在/相关性"（高风险）入人工清单。
3. **E.1 触发 = 确定性信号预筛 + 批判 agent 复核**（不靠模型自报置信度——抓不到"自信地错"）。
4. **E.1 = 独立 `review/` 模块**（方案 A），跑在已落库的 projects.db 上，与提取解耦、可单独重跑、可对存量补跑、可被 eval 验证；结构对称于 `eval/`。
5. **批判 agent 默认 DeepSeek V4 Pro**（更强模型做"怀疑式第二眼"；低频只跑预筛子集，成本可控）；提取主链仍 V4 Flash。
6. **E.2 `chinese_unnamed` 进主库 + 占位实体 + 进补名清单**（确有中企的真项目不丢、可计数、可跟进）。
7. **E.1 + E.2 共用同一个复核清单** `review.db.review_queue`（reason_type 区分）。
8. **关注点解耦**：提取(s01b)=尽力提+标 unnamed；复核(review/)=挑刺纠错+兜底入清单；验证(eval/)=证明无退化/有提升。

## 架构与模块

```
review/                         # E.1 独立复核模块（新建，对称 eval/）
├── signals.py                  # 确定性预筛：读 projects.db → 可疑候选(project + 可疑字段)
├── critic.py                   # 批判 agent：原文+提取 → 逐字段质疑核验 + 挑战相关性 → verdicts（pydantic 校验）
├── apply.py                    # 分流：字段高置信→事务改库；status挑战/存疑/unnamed→写 review_queue
├── run_review.py               # CLI 编排：signals → critic → apply → review report；支持 --dry-run
└── __init__.py
# 取原文复用 eval/article_store.get_article；LLM 复用 s01b llm/client
```

E.2 改动落在 **s01b 内**（提取阶段）+ 下游最小处理，不单独建模块。

## E.1：低置信二次核验（独立 review/ 模块）

### signals.py（确定性预筛，不调 LLM）
读 projects.db，命中任一信号即成候选并记可疑字段：
- 实体 = `Unknown`（应有名却没提到，区别于 unnamed 占位）；
- 该 category 本该有容量（非 no_capacity）却 `capacity_mw` 空；
- `involvement_type` = Unknown / 空；
- S5 产生过 `confidence<0.8` 未采纳的纠正建议；
- 跨字段冲突（如项目名含"光伏"但 category≠光伏）。
作用：把全量压到小可疑子集，控制 critic 调用成本。

### critic.py（批判 agent，每可疑项目一次调用，默认 V4 Pro）
- 输入：原文全文（`eval/article_store.get_article`）+ 该项目提取记录。
- 角色 = 怀疑的核查员：
  - 每个可疑字段：原文支持吗 → `{field, verdict: ok|wrong|unsupported, suggested_value, confidence, evidence}`；
  - **额外挑战相关性/存在性**：是否真为"中国参与的可再生能源项目"，还是油气/矿业/民用被误收（直打 status 过度收录弱项）。
- 输出经 pydantic 校验（verdict 枚举、confidence∈[0,1]、类型）后才进 apply；非法立即抛错（外部数据边界）。

### apply.py（分流 = 两者结合）
- 字段值纠正 + critic 高置信 + 有原文依据 → **事务自动改 projects.db**，记变更日志（低风险：category/capacity/role 等）。
- 相关性/存在性挑战（status_challenge）→ **不自动删**（高风险）→ 写 `review_queue` 人工确认。
- 仍存疑 / critic 拿不准 → 写 `review_queue`（low_confidence_field）。

### 数据流
```
projects.db ──signals──► 可疑候选 ──critic(原文+提取, V4 Pro)──► verdicts(pydantic 校验)
                                                          ├─ 字段高置信纠正 → 事务改 projects.db(记日志)
                                                          └─ status挑战/存疑/unnamed → review_queue(review.db)
                                                                                          └─ 人工 CSV 往返 → 回写
run_review → review report（候选数/自动改数/入清单数/reason 分布）→ 再跑 eval 验证
```

### review_queue 表（review.db 新表，E.1+E.2 统一）
`id, canonical_id, source_link, reason_type(unnamed_entity|low_confidence_field|status_challenge), field, current_value, suggested_value, critic_confidence, evidence, state(pending|resolved), created_at`

### 人工处理工作流（复用 eval 同款）
`run_review` 后导出 review_queue pending 项为 CSV → 人工逐条裁决 → 小脚本回写 + 标 resolved。**本期可先只做导出 CSV；回写脚本若来不及，留作紧接小迭代**（避免 P2 过大）。

## 错误处理（遵 CLAUDE.md）

- critic LLM 调用走 `llm/client` 重试/退避（429≥30s、5xx 指数退避、403 终止）；单项目 critic 失败 → `logging.error`(含 source_link) + 计 `n_critic_failed`，跳过不中断。
- critic 输出未经 pydantic 校验**禁止**进 apply（规则 6）。
- 自动改库**事务包裹**；run 前对 projects.db 做 `.bak` 备份（动主库前先备份）；逐条记变更日志（canonical_id/字段/旧→新值/critic 依据），可回滚可审计。
- `run_review.py` CLI 入口 pydantic 校验（db 路径存在、阈值范围、`--dry-run` 只出报告不改库）。
- 无静默 except；status_challenge 一律不自动删，只入清单。

## 测试策略（TDD，对称 eval/，全程 `uv --project s01b_project_extractor run`）

- `signals.py`：合成项目 → 断言挑出预期候选（每信号一个用例）。
- `critic.py`：注入 mock LLM → 断言 verdict 解析 + pydantic 校验；含"非法输出→抛错"用例。
- `apply.py`：断言分流正确（字段高置信→改临时 db；status挑战/存疑→入清单不改库）；事务/备份/变更日志。
- `run_review` e2e：mini projects.db + mock critic → 跑通 → 断言 report 数字 + review_queue 写入 + `--dry-run` 不改库。
- E.2：S1 对"未点名"样本判 `chinese_unnamed`（mock）、写库占位实体、status 全链（gold_loader/predict）接受 4 值。

## eval 验证口径（P2 验收证据）

1. **先复查 gold**：97 篇里"有中企未点名"的 status 改标 `chinese_unnamed`，重跑出 4 值口径新基线。
2. **验 E.2**：落地后重跑 eval，status 应更准（unnamed 不再误判 no_chinese/Unknown）。
