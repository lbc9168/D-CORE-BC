# v2.1 二次复核（带原文 AI recheck）设计

> 日期：2026-06-17。worktree `worktree-v2`。
> 上游：`docs/status/backlog-v2.1.md` F 节（设计草案）；本 spec 将其落为可实施设计。
> 关联：Phase B（B3 重建已完成）；本步是 backlog F 计划落点 = **在 B3 之前**改 `extracted_projects`，随后重跑 B3→B7。

## 1. 目标（Goal）

对 C2 dry-run 入队、第一遍 critic **拿不准没给出可用值**的高/中 severity 候选，做**第二遍带原文 AI 复核**：用配置化更强模型 + "强制决策" prompt + 回喂第一遍 verdict，逼出每个可疑字段的最终结论（确认/纠正/排除/仍存疑）；**分层自动落库**到 `extracted_projects`，仍存疑的进一个**小残留清单**。然后重跑 B3→B7 让纠正/排除流进 canonical 与网页。

## 2. 背景与候选集（Context）

- C2 dry-run（2026-06-03）把可疑字段入 `review.db` 的 `review_queue`，**未自动改的**那批留作人工/二次兜底。
- severity 打标（`scripts/oneoff/tag_review_queue_severity.py`，确定性算）：**高 57 / 中 854 / 低 3502 / None 61**（总 4474）。
  - **候选 = 高+中 = 911 条 queue items，跨 859 个 distinct 记录**（`canonical_id` = `extracted_projects.row_id`）。
    - 高 57 = 56 `exclude_suggested`（critic 判该排除但 conf<1.0）+ 1 `low_confidence_field`。
    - 中 854 = `low_confidence_field`（category 类别挑战 / involvement 真换角色 / capacity≥30%变 / project_name 真纠正）。
  - 低 3502 维持原值，不复核。
  - > 注：backlog F 写的"高 1 / 855"为旧打标（`output/tag_severity.py`）的过时数；以本库实测 **高57/911** 为准。
- 第一遍 critic（`review/critic.py`）**已经喂过原文**——第二遍的增量不是"终于给原文"，而是 **更强模型 + 强制决策 prompt + 回喂第一遍结论作上下文**。
- 候选与 B1 replay 已自动应用的 2114 条 would_change **不相交**（queue 里是 low_conf/exclude_suggested 这类"未自动改"的），无双改风险。
- `extracted_projects.row_id` 稳定（B1 replay 只 UPDATE 未删行），queue 仍能 join 回。

## 3. 范围（Scope / YAGNI）

**做**：高+中 911 候选的二次复核 + 分层 apply 到 extracted_projects + 残留 CSV；随后重跑链。
**不做**：低 severity 3502（维持原值）；通用去重重设计；前端改动；把 recheck 并进日常 `run_review`（backlog 提的"将来并入"留作后续）。

## 4. 架构（方案 1：新薄模块最大复用）

新建 `review/recheck.py` 作编排器，**复用** `review/` 现有件：
- `review.critic.Verdict` / `review.critic.review_project`（critic 调用 + pydantic 校验）——新增"recheck 变体" prompt。
- `review.apply.route`（分层 apply 二次闸：exclude 仅 conf=1.0 自动、字段 wrong 高置信+过校验自动、status 永不自动、其余入队）。
- `review.run_review` 的 `_make_update_field` / `exclude_field` 闭包（写 `extracted_projects`，白名单防御 + capacity 走 `bri_parse`）——抽出复用。
- `review.run_review.get_article` / `article_store`（按 source_link 从 raw_news.db 取原文）。
- LLM：`s01b_project_extractor.llm.client`（provider/model 配置化，默认 `deepseek` + `DEEPSEEK_MODEL`=v4-pro，env 可换）。

> 不改 `run_review.py` 本体（已 22KB）；只把它内部的 update_field/exclude_field 工厂抽成可复用入口（若已模块级则直接 import）。

## 5. 组件与接口（Components）

### 5.1 `review/recheck.py`（新建，编排器）
- `load_candidates(review_db, projects_db) -> list[Candidate]`：读 `review_queue` WHERE `severity IN ('高','中')`，按 `canonical_id`(=row_id) 聚合成"每记录一组可疑字段 + 各自第一遍 verdict 上下文"；join `extracted_projects` 取当前字段值与 `source_link`。
- `run_recheck(projects_db, raw_news_db, review_db, *, llm=None, dry_run=True, residual_csv, ...) -> dict`：编排 取原文→recheck critic→apply 分层→残留 CSV→JSON report。结构/签名对齐 `run_review.run_review`（dry_run、自动 .bak 备份、逐条错误隔离、would_change 累加）。
- 返回 `{candidates, rechecked, auto_corrected, auto_excluded, residual, critic_failed, would_change}`。

### 5.2 critic recheck prompt（在 `review/critic.py` 旁新增）
- `_build_recheck_prompt(*, article, project, suspicious_with_prior) -> str`：在第一遍 prompt 基础上多两件事：
  - (a) 对每个可疑字段注入第一遍 `{verdict, confidence, evidence}`，明示"上次你标了可疑但没给可用值"；
  - (b) 指令"对着原文**对每个字段必须落最终 verdict**（ok / wrong+合法值 / unsupported / exclude），不得再只回'可疑'"。
- 复用 `Verdict` schema 与合法枚举注入（category/involvement 仍从 `bri_enums` 注入）。
- `recheck_project(*, article, project, suspicious_with_prior, llm) -> list[Verdict]`：薄封装，等价 `review_project` 但用 recheck prompt。

### 5.3 apply（复用 `review.apply.route`，按 5.6 配置阈值）
- 注入：`update_field`（写 extracted_projects，白名单 + capacity 经 `bri_parse`）、`exclude_fn`（`excluded=1, exclude_source='recheck'`）、`value_validator`（category/involvement 必合法枚举、capacity 必正数、**project_name 直接判 False → 强制入清单**）。
- 残留（queued）落 `recheck_residual.csv`（复用 `export_queue` 思路，或直接写 CSV）。

## 6. 数据流（Data Flow）

```
review.db.review_queue(severity∈{高,中}, 911)
  └─ load_candidates ─→ 859 记录 × {可疑字段 + 第一遍 verdict 上下文 + 当前值 + source_link}
        └─ get_article(source_link, raw_news.db[主仓库，只读]) ─→ 原文 title/content
              └─ recheck_project(LLM=deepseek v4-pro，强制决策) ─→ [Verdict]
                    └─ apply.route(分层二次闸)
                         ├─ exclude conf=1.0          → extracted_projects.excluded=1 (source=recheck)
                         ├─ field wrong 高置信+过校验   → UPDATE extracted_projects (capacity 经 bri_parse)
                         ├─ project_name 任何情况       → 残留 CSV（强制不自动）
                         └─ status / 低置信 / 无值      → 残留 CSV
```

dry_run=True 时上面写库全部走 would_change 累加、不实改（与 run_review 一致）。

## 7. 分层 apply 哲学（已与用户确认）

| verdict | 条件 | 动作 |
|---|---|---|
| exclude | conf=1.0 | 自动 `excluded=1`（可逆，记 evidence） |
| exclude | conf<1.0 | 残留 CSV |
| wrong（category/involvement/capacity） | 有建议值 + conf≥阈值(0.8) + 过 value_validator | 自动改 extracted_projects |
| wrong（project_name） | 任何 | **强制残留 CSV**（C2 张冠李戴教训） |
| status / unsupported / 无建议值 / 校验不过 | — | 残留 CSV |

## 8. 重跑链 B3→B7（落点 = B3 之前）

recheck 改的是 `extracted_projects`；随后**重跑**：
1. **B3** s02a 重建（`run_b3_rebuild.py`，trust_dedup=True，**dedup_cache.db 命中加速**）→ 新 canonical/events/entities。
2. **B4** `normalize_entities`、**B5** `normalize_locations`（清空 location_norm 后用已修复的 bri_location 跑）。

> 重跑链本身不在 recheck 模块代码范围内，是 recheck 落库后的**执行步骤**（实施计划里单列、GATED、花 LLM、改库需人值守）。

## 9. 错误处理

- LLM/解析失败：统一 client 重试退避后抛出；recheck 编排逐条 try 隔离（一条挂不连累整批），计 `critic_failed`，该条留 queue 不动。
- 改库前自动 `.bak`（复用 run_review）。
- raw_news.db 缺原文（取不到）：跳过该条、计数、留 queue。
- 候选 join 不到 extracted_projects（row_id 失配）：跳过 + 警告（理论不应发生）。

## 10. 测试（TDD，LLM 全 mock）

- apply 分层：exclude conf=1.0 自动 / conf<1.0 入清单；category 高置信自动、capacity 经 bri_parse、project_name 强制入清单；status 入清单。
- dry_run：不实改、would_change 正确累加。
- e2e：fake LLM 给定 verdicts → 正确分流 + 残留 CSV 行数。
- 复用现有 review 测试夹具（fake llm、tmp db）。

测试运行：`uv --project s01b_project_extractor run pytest tests/ review/ -q`（与现有 review 测试同 venv）。

## 11. 风险与防呆

- **只读主仓库 raw_news.db**（读不算碰主工作区）；recheck 写的是 worktree projects.db。
- **不碰 C2 已自动应用的 2114**（候选是未自动改的 queue 项，不相交）。
- **capacity 自动改必经 `bri_parse`**（防 '1000-1200' 塞 REAL）。
- **project_name 永不自动改**。
- recheck 是"第二遍兜底"，模型仍可能错——**dry-run 报告先给用户看** would_change，认可后才非 dry-run 落库。
- 重跑链改主库前 `.bak`；6 组合并改的是**重建后的新 canonical**，重新检测决策。
