# v2.1 P0 设计：金标准评测集 + 评测框架

> 创建：2026-05-24
> 性质：设计文档（spec）。经 brainstorming 与用户确认。实施计划另由 writing-plans 产出。
> 上游：[v2.1_plan.md](../../rules_and_plans/v2.1_plan.md) P0。

## 目标（一句话）

为 s01b 提取步骤建立一把"尺子"：~150 篇人工核定的 ground truth + 字段级准确率评测框架，使 P1 起的每次 prompt/agent 改动都能量化判断是进步还是退步。

## 范围界定

- **只评 s01b 提取**（文章 → 提取字段），不评端到端管线、不评去重。
- 不改生产数据；评测全程读 `raw_news.db`（取原文）+ 跑提取器到临时位置，不写 projects.db / bri_re_database.db。

## 架构与组件

```
eval/
├── gold_set.jsonl        # ground truth：每行 {article_id, source_link, labels{...}}（不含全文）
├── build_draft.py        # 从 extracted_projects 抽样分层 → 生成待改正草稿
├── run_eval.py           # 跑提取器于 gold articles → 与 labels diff → 字段级报告
├── metrics.py            # 各字段类型的比较器（enum/数值/实体/相关性门）
├── cache/                # 按 article_id 缓存提取器输出，避免重复花 Gemini 钱
└── reports/              # 每次评测的字段级报告（带时间戳，可对比上次）
```

### 1. Gold set（`gold_set.jsonl`）

- **规模**：~150 篇。**分层抽样**覆盖：每个 category（光伏/风电/水电/地热及余热/生物质/储能/综合能源/核电/火电/输变电建设/新能源制造业）+ 难点桶（容量反推、数据中心、设备主/次、未点名中企、多中企、no_chinese、irrelevant 各若干）。
- **不存全文**（版权/体积）：每条只存 `article_id` + `source_link` + 标注字段；评测时按 id 从 `raw_news.db` 取正文。`gold_set.jsonl` 可进 git（不含敏感全文）。
- **每条 labels 结构**（对齐 extracted_projects 字段）：`status`(valid/no_chinese/irrelevant)、`category`、`capacity_mw`、`storage_*`、`project_stage`、`location`、`total_investment_usd`、`financing_model`、`involvement_type`、中方实体列表(`entities[]`)、…（自由文本 summary 不标注）。

### 2. 标注工作流（AI 草稿 + 人工改正）

1. `build_draft.py`：从 `extracted_projects` 分层抽 ~150 篇，导出"草稿"（含 AI 现有提取值 + source_link）为可编辑文件（建议 CSV/JSONL）。
2. 用户**对照原文逐条改正**（必读原文，防止顺手放过 AI 错），定稿。
3. 定稿转为 `gold_set.jsonl`（标注 = 正确值）。

### 3. 评测指标（`metrics.py`，按字段类型）

| 字段类型 | 字段 | 比较器 | 算对的判定 |
|---|---|---|---|
| 相关性门 | status | 精确 | 完全相等（错则整条记错，单列报告） |
| 枚举 | category/project_stage/involvement_type/financing_model | enum 归一后精确 | 经 enums_mapping 归一后相等 |
| 数值 | capacity_mw/total_investment_usd/storage_* | 容差 | **±5%** 内算对；一方有值一方空 = 错 |
| 实体集合 | 中方实体（可多个） | 集合 P/R/F1 | 名称归一后按集合算 precision/recall/F1 |
| 自由文本 | project_summary | 不计入硬分 | （可选单列，不影响总分） |

- 报告输出：**每字段准确率** + **加权总分** + **与上次报告对比**（↑/↓）。
- 相关性门是前置：status 判错的样本，其字段不再计入字段准确率（避免双重惩罚），但单独高亮。

### 4. 评测框架（`run_eval.py`）

- 输入：`gold_set.jsonl` + 当前提取器。
- 流程：对每篇 article_id 从 raw_news.db 取原文 → 跑当前提取器（**结果按 article_id + 提取器版本 hash 缓存**到 `cache/`，命中则不重调 Gemini）→ 与 labels 经 `metrics.py` 比较 → 写 `reports/<timestamp>.json` + 控制台摘要。
- 工作流：改完 prompt/agent → `python eval/run_eval.py` → 看各字段准确率变化 → 决定保留/回退。

## 数据流

```
raw_news.db ──(article_id)──► run_eval ──► 当前提取器 ──► 提取输出(缓存)
                                  │                          │
gold_set.jsonl(labels) ──────────┴──► metrics 比较 ─────────┘──► reports/字段级报告
```

## 错误处理

- 提取器对单篇报错：记为该篇"提取失败"，不中断整体评测，报告里单列失败计数（遵守 CLAUDE.md 规则1，捕获具体异常 + logging）。
- raw_news.db 取不到某 article_id：跳过并 warning。
- Gemini 调用：按现有重试/退避；缓存命中优先。

## 测试策略

- `metrics.py` 各比较器单测（数值 ±5% 边界、enum 归一、实体集合 F1、status 门）。
- `run_eval.py` 用 mock 提取器 + mini gold set（3-5 条）跑通流程、生成报告（不调真实 Gemini）。

## 单一可信源/规则遵循

- 枚举归一复用 `bri_enums`；数值解析复用 `bri_parse`（±5% 容差与去重一致）。
- 评测缓存避免重复 Gemini 花费；`.env` 提供 API key，不入 git。

## 开放项（实施时定，非阻塞）

- 草稿编辑格式：CSV（Excel 友好）vs JSONL（结构清晰）——倾向 CSV 便于人工改。
- 加权总分的权重（相关性门/枚举/数值/实体如何加权）——倾向等权或相关性门更高，实施时给默认可调。
