# v2.1 P2.1 设计：exclude 机制 + 录入范围对齐 + critic 枚举约束

> 工作区：worktree `E:\Projects\BRI_RE_Database_v2\.claude\worktrees\v2`（分支 `worktree-v2`）；遵守该 worktree `.claude/CLAUDE.md` 全部规则。

## 目标（一句话）

把"该不该在库里"做成**一等公民的可逆 exclude 标记**（提取先标、v4-pro review 确认），统一提取/review 三层的"录入范围"定义，并约束 critic 只产合法枚举值——从而消灭"critic 发现该排除却无法排除、只能把非法值硬塞进 category/involvement 硬约束字段"的乱象。

## 背景与根因（P2 全量 dry-run 暴露，已核对源码）

P2 复核机制（`review/`：signals/critic/apply/run_review/queue/export_queue）已落地，对存量库（s01b `extracted_projects`，~10815 行）跑过全量 dry-run：3351 候选中 **1586 条被 critic 判 status_challenge（疑该排除）**，且大量 `suggested_value` 落在枚举外（"天然气"/"海洋油气"/"Equipment Supply"/"Equity"）。根因四条：

1. **三层"范围"定义不一致**：
   - S1（`s1_relevance.py`）：范围 = "电力/发电项目"（任何燃料含火电，recall-first）。
   - S2（`s2_basic.py`）：表头写"可再生能源/电力项目"；A.1 把火电/燃机/煤电→category「火电」（火电当前 `excluded:true`）。
   - critic（`review/critic.py`）：按"可再生能源项目"判 → 把火电/天然气/油气一律报 status_challenge。
   - → critic 不知道"火电是合法类别"，对提取层已分类好的火电记录重复报 status 问题（dry-run 里 405 条"化石/油气"多半是此）。
2. **提取链无 exclude 出口**：真相是"油气/化工/民用"时根本没有合法 category 可填，模型被迫挑「综合能源」；critic 发现了也排除不了 → 借 category/involvement 表达 → 产生枚举外建议。
3. **「综合能源」被当兜底桶**：S2 只教了"混合发电→综合能源"，未规定"S1 漏放进来的油气/化工/民用怎么办"；S2 默认"已是项目"只管归类，不复核相关性 → S1 的漏判原样穿过，堆进「综合能源」。
4. **critic 不受枚举约束（与 S5 不一致）**：`s5_summary.py` 自检明确要求 suggested_value 必须是合法枚举且只动 stage/category，很规矩；而 `review/critic.py` 没把枚举清单喂给模型、也不约束建议值 → 发明枚举外值。

## 录入范围（确定）

录入只保留三类（recall-first，宁可多收再筛）：
1. **发电项目**（任何燃料，含火电/燃气/煤电/核电）；
2. **新能源制造业**（电池厂/组件厂/光伏板/多晶硅厂等，以 GW/年、万吨/年计产能的工厂）；
3. **输变电/电网工程**。

不录入（irrelevant）：油气开采/炼化/管道/LNG 接收储运、采矿冶炼、纯民用基建（学校/医院/机场/铁路/港口/灌溉/供水/数据中心/住宅/工业园区本身）、纯运维检修、纯总量框架/MOU、纯评论综述榜单、纯领导访问视察（无具体项目节点）。

> ⚠️ 之前 S1 只问"电力/发电项目"——**新能源制造业（组件厂/电池厂）不发电，可能被 S1 当工业园区挡掉**；本设计把 S1 范围显式扩到上述三类。

## 核心设计决策（用户已拍板）

1. **火电不再排除**：category「火电」`excluded:true → false`（火电属发电项目，必须录入保留）。`hidden` 暂不强制改（保持现状 false），前端是否隐藏以后再定。
2. **exclude 是可逆标记，不是删除**——红线"status/存在性永不自动删"不破；误标可一键翻回。
3. **exclude 落点**：加到 s01b `extracted_projects`（新列），并在 s02a 去重时**传播到 `canonical_projects.excluded`**（前端最终认 canonical.excluded）。
4. **review 自动排除自治度**：critic 的 exclude 判决 **conf=1.0 → 自动置 excluded=1**（记日志、可逆）；**conf<1.0 → 入人工清单**抽检。
5. **统一范围**：提取与 review 全部用"电力/发电（含火电）+ 新能源制造业 + 输变电"，**全程不再出现"可再生能源"窄词**。

## 改动清单

### A. 枚举（`enums_mapping.json`，单一可信源）
- category「火电」：`excluded:true → false`。`hidden` 保持现状。
- ⚠️ 改 schema/枚举：只改 enums_mapping.json；若涉及主库列变更，动主库前 `.bak` 备份。

### B. prompt 修改
- **`prompts/s1_relevance.py`**：第一步范围从"是否电力/发电项目"扩为"是否属于 ①发电（任何燃料含火电）/②新能源制造业（电池/组件/光伏板/多晶硅厂）/③输变电电网 任一"。命中任一进第二步。排除项保持（油气/采矿/民用/运维/框架/评论/视察）。recall-first（"存疑倾向算"）不变。
- **`prompts/s2_basic.py`**：
  1. 表头"可再生能源/电力项目" → "电力/发电（含火电）、新能源制造业或输变电项目"；全程删除"可再生能源"窄词。
  2. **收紧「综合能源」**：明确"综合能源仅指多种**发电类别**的组合（如光伏+风电+储能）；油气/化工/民用/水务/灌溉一律**不是**综合能源、也**不应成为项目**"，给正反例。
  3. **加 exclude 出口**：每个项目输出新增 `in_scope: true|false` + `out_of_scope_reason`。S2 若判某条实为油气/化工/民用（S1 漏放），recall-first 仍记录但 `in_scope=false`。
- **`review/critic.py`**：
  1. 挑战范围从"可再生能源项目"改为"电力/发电（含火电）/新能源制造业/输变电 且有中企参与"。
  2. 把合法 category/involvement 枚举清单注入 prompt（照 `s5_summary.py` 范本）；字段纠正只许从清单选，选不出走 exclude/unsupported。
  3. `Verdict` 模型新增 `verdict="exclude"` 值；critic 判非范围/无中企时走此通道，**不再**借 category/involvement 表达。

### C. exclude 机制（schema + 写库 + review + 传播）
- **schema**：s01b `extracted_projects` 加列 `excluded INTEGER DEFAULT 0`、`exclude_reason TEXT`、`exclude_source TEXT`（`extraction|review|manual`）。迁移加进 `tools/project_extractor_tool.py` 的 `_init_projects_db` ALTER 列表（`try/except sqlite3.OperationalError` + 注释，规则1允许的无害边界）。动主库前 `.bak`。
- **写库（extraction）**：S2 的 `in_scope=false` → 写 `excluded=1, exclude_source='extraction', exclude_reason=out_of_scope_reason`。
- **review（apply）**：`review/apply.py` 新增 exclude 分流——critic 的 `exclude` 判决，`conf>=1.0` → 经注入的 update 闭包置 `excluded=1, exclude_source='review'`（事务、记日志、走 run_review 白名单机制，dry-run 只记 would_change）；`conf<1.0` → 入 `review_queue`（reason_type 用新值如 `exclude_suggested`，或复用 status_challenge——实施时定）等人工抽检。
- **传播（s02a）**：`s02a_duplicate_merger/.../tools/duplicate_merger_tool.py` 去重合并时，把成员记录的 `excluded` 传播到 `canonical_projects.excluded`（规则：任一成员被排除即排除，或多数表决——实施时定一个并加注释）。canonical_projects.excluded 现 0:4373 / 1:34。

### D. 顺带修（P2 dry-run 已暴露，与本任务相关）
- review 自动改写 `capacity_mw` 时写的是 critic **原始建议串**（如 `'1000-1200'`/`'近90'`/`'10000 MWh (年产能)'`）→ 污染 REAL 列。应改写 `bri_parse.parse_number()` 解析后的数值。
- `project_name` 自动改写偶发"张冠李戴"（critic 串项目，如 id4106 把巴西项目串成墨西哥）→ 建议 `project_name` 改为**只入人工、不自动改**。

## 验证口径（重要——已按成本/有效性修订）

> 背景：S1/S2 是**提取侧** prompt，**未重新录入数据时，在旧库上重跑 review 测不出 S1/S2 的效果**（旧库是旧 prompt 提的）。且全量 review 一次 ~¥40，不必反复烧。

1. **单测 / e2e（mock LLM，零 LLM 成本）= 主检**：覆盖 exclude 路由（conf=1.0 自动 / conf<1.0 入队）、in_scope=false→写 excluded、s02a 传播、capacity 写解析值、project_name 转人工、critic Verdict 新增 exclude 值的校验、enum 注入后非法建议被正确处理。**正确性主要靠这层。**
2. **critic 侧改动 → 小样本 real-LLM dry-run 抽验**（~几十条，deepseek-v4-pro，复用既有 ~32 候选临时库即可；成本极低）：确认在真实数据上 (a) exclude 判决出现并正确分流、(b) would_change/队列里**不再有枚举外的 category/involvement 建议**、(c) **火电记录不再被报 status_challenge**（范围对齐生效）。**不跑全量。**
3. **提取侧 S1/S2 改动 → eval 重跑（97 篇金标准，有界成本）**：用 `eval/run_eval`（带 `--raw-news-db` 指主仓库 raw_news.db）重提取 97 篇打分，看 S1 范围扩展（纳入制造业/输变电）+ S2 收紧后 status/字段**不退化、最好有提升**。这是提取 prompt 改动的**正确**检验，而非 review 全量。
4. **真跑改库（去掉 --dry-run）前**：把 dry-run report 给用户看、经其同意；改主库 schema 前 `.bak`。

## 错误处理 / 规则遵循

- 禁裸 except；唯一允许沉默的是 ALTER 列已存在（`except sqlite3.OperationalError` + 注释）。其余异常指定类型 + `logging.error`。
- exclude 改库走事务；自动置 excluded 记变更日志（id/旧→新/critic 依据），可回滚可审计。
- 枚举只走 bri_enums，数值走 bri_parse；status/exclude 是管线状态值，就近加常量。
- API key 经 `.env`（不入 git）；report/CSV/.bak/`*_review.db` 等本地产物 gitignore。
- 每个 session 结束同步更新 `docs/status` 与 `docs/changes`。
