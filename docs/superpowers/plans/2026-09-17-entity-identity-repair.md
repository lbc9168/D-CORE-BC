## 已确认的职责混淆与维护问题

1. 名称规范化表被扩展为项目准入白名单；原文明示中企的合法证据通路未在 Python 门禁中实现。
2. 同一法人别名、实际子公司和统计集团归属混在同一层级结构。部分二级集团按历史决定独立成组；该表不等同于完整的直接母公司/最终控制人股权树。
3. S01B 输出集团+原文 subsidiary，S02B developer 输出法律主体自身规范名。两种视角可共存，但不应隐含地共用“canonical”语义。
4. subsidiary_name 同时容纳原文别称与真实子公司；缺少独立且稳定的法律实体键。S02A 的 _merge_group 仍按集团+角色去重，与其他路径三字段去重不一致。
5. 参与事实验证依赖角色词白名单。角色无法确定时会删除实体，随后写 Unknown；应区分参与是否成立和角色是否确定。
6. 新记录的待复核 excluded 通过 OR 传播到历史 canonical；本次已有13个历史项目受影响。
7. 维护源发生漂移：将 build_hierarchy_v2.main 的输出替换为内存缓冲，重建结果仍为151组，但两个组与现行表不同：会缺失国家电投的“中电国际/国家电投中电国际”别名，以及“三峡发展（马）公司”条目。未运行真实写文件生成。重建入口需要保护后补裁决。
8. 翻译缓存并非全部人工核实；不能用于证明企业身份、股权归属或法律主体相同。

## 用户已确认的业务原则

- 不区分国企、民企：集团母公司为中企时，沿已确认的母子关系将下属企业认定为中企，包括多级子公司。不以海外注册地单独否定这一研究口径。
- 必须保留一份统一、严格核实的企业主表，表达企业主体、集团多级母子关系和别名；本次修复优先保证其正确性。
- 项目提取和正式企业入册使用不同要求。企业名称未入册不等于项目不应收录；先保留有依据的中企参与，再处理名称和集团关系规范化。
- 新项目涉及企业分为已记录企业和此前未记录企业，流程应清楚、简洁。主表更新的具体证据标准与操作机制尚待讨论，不将模型建议自动认作正式关系。
- Developer 可以是中企或外企；只有原文明确证明该主体在目标项目中的 developer/业主身份，才可填写。企业已入册、属于中企集团或参与了项目均不足以认定 developer；本次放宽名称未命中处理不放宽 developer 证据要求。

## 已采纳的设计原则

### 统一企业事实、独立项目角色、一个待补录清单

- 企业主表每个实际主体有独立稳定 ID；同法人别名指向该 ID，子公司有自己的 ID。规范英文名和常用缩写也归到该主体，两个旧翻译缓存仅作为待核实翻译来源，不能认证身份。
- 主表核心信息：主体 ID/规范名/别名/直接母公司 ID/集团母公司 ID/集团身份依据，以及每条关键事实的来源、核实时间。英文名可缺，不阻止主体建立；物理存储格式留到实现设计阶段。
- `chinese_entities` 继续记录项目事件中的实际企业、原文名、参与证据和角色，并关联主表主体 ID。集团归属通过主表获得，不再用集团名覆盖实际参建企业。
- 未命中名称及其原文证据、候选主体、受影响项目进入一个统一待补录清单；该清单不具备正式主表的权威性。
- 已确认外企可纳入共享企业事实层以避免反复误判；统一企业事实不意味着所有企业都是中企，也不意味着任何企业自动具有 developer 角色。
- 物理合并 company_hierarchy 与 developer_registry 不是本轮必要前提，仍为待定建议。可以保留两个文件/用途视图，先统一主体 ID、可信别名引用和字段语义；不能把文件合并作为解决角色误判的手段。

### Developer 的独立证据契约

- 企业事实层只回答主体、名称、母子关系、中企身份，不提供全局 is_developer 标识。Developer 是某主体在某个项目/事件中的关系，必须按目标项目分别判断。
- 按原文提取 developer 候选及对应证据，验证该证据确实支持目标项目与该主体的业主/开发商身份，再使用企业登记表规范化该主体名称；查表函数不能从参与企业列表自动生成 developer，也不能把空 developer 补成中企名称。
- 原文不必出现英文 developer 单词，但必须有明确支持既定 developer 定义的表述。承包、供货、融资、一般合作、候选名单以及一般性的“中标”均不能单独证明开发商身份；不能用既有角色标签反推原文已经证明 developer。
- 某子公司是项目 developer，不自动将集团母公司、兄弟公司或其所有股东写为 developer。集团统计可以上卷，developer 事实保持实际主体。
- 多企业及多项目原文中逐个绑定证据，不能用一段非空引文为名单中的全部企业背书。Developer 证据不足仅清空该字段，不否定其他充分的中企参与事实。
- 现行 developer_check 已检查空证据、候选名单及部分角色冲突，但这些负向检查不能视作完整的项目—主体—developer 正向证据验证。本轮保留既有保护并针对该契约验证。
- 必须覆盖的回归样本：外企业主+中企EPC、中企仅供货、已在册企业但无业主证据、某企业是项目A业主但仅参与项目B、子公司业主不提升母公司、多企业仅一方有业主证据。均要求 developer 只包含有该项目原文依据的主体。

### 简化的运行路径

1. 提取企业原文名及项目参与证据，身份、角色、融资证据分别判断。
2. 已在册且匹配无歧义：关联主体 ID，读取直接母公司和集团关系，沿已确认关系继承中企身份；查表本身不证明参与当前项目。
3. 未在册或匹配有歧义：保留原文与候选。项目若另有充分中企参与依据，不因名称缺口排除；没有充分身份依据的部分保留待核实，不假定中企、不写正式集团归属。
4. 每轮更新汇总一个待补录清单，按候选企业及其影响项目集中核实。确认后做添加别名/新增主体/补充关系等明确操作。
5. 入册后仅重新解析受影响项目，保留项目与事件 ID；集团统计仅使用已确认归属，未归组记录单独标示，不虚构归属或把同名候选当作已确认唯一企业。

### 存量表正确性优先

- 当前 hierarchy 的 subsidiaries 是扁平列表，子条目只有 name_cn/legal_full_name_cn；不能据此恢复一级、二级、三级的直接母子关系，也不能把所有条目直接挂成集团一级子公司。
- 迁移先逐项核对现有名称、别名、身份与关系证据；已有用户确认裁决保留。已知属于某集团但中间层级未明时，只记录已证实的集团归属，直接母公司暂缺。
- 一个关系有证据不代表其他关系自动成立；别名证据、母子关系证据和集团中企身份证据分别保留。少数股权投资、合作或品牌授权不得在没有母子关系依据时自动当作子公司；具体合资边界另行裁决。
- 模糊相似、模型常识、翻译结果只能提出候选。确认的修改须可追溯、可回滚，生成输出不得覆盖已确认的后补裁决。
- 先完成结构/冲突审计和证据覆盖盘点，明确“已确认/待核实”；不能把旧表导入或单纯结构校验说成已完成真实性核实。外部证据核实范围与成本在执行前单独明确。

## 实施顺序与验证目标

1. 先审计与整理企业主表，形成字段示例、冲突/证据缺口清单和可核验样本；具体入册标准随更新机制讨论收敛。
2. 接通已在册/待补录两条运行路径；修复角色不明删实体、排除状态传播和不一致的实体去重键。
3. 在隔离数据库快照上定向恢复受影响记录；普通增量重跑会跳过已处理 URL/已导入记录，不能整批取消排除。

完成标准：多级中企身份沿确认关系正确继承；同法人别名一致、不同子公司不误并；新企业有参与依据时不因未入册丢项目；明确外国企业不误作中企；角色不明不抹掉参与事实；新事件待核实不影响历史确认记录；重放不新增重复项目/事件，生产源库保持不变。
