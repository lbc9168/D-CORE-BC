### DuplicateMergerTool（五阶段，纯 Python + LLM）

1. **数据加载**：读 `projects.db` 中 `imported_to_s02a=0` 的记录，按 `record_type` 分流——
   - `具体项目` → 进入去重流程；
   - `设备订单` / `一般合作` → 直接写 `non_project_records` 表，跳过去重；
   - 归组后对 `location` 为空的"具体项目"批量调 LLM 从项目名补省/城市，提升去重判断质量。
2. **候选筛查**（多信号 OR）：CN 名 `token_sort_ratio≥85` / EN 名 `≥80` / CN `partial_ratio≥90`（子串）/ 容量精确匹配（误差≤1%，最小 50MW）/ 共有实体 + 名称中度相似(≥60) 辅助通道 / 宽松候选（名称≥40 且实体重叠或容量 15% 内）/ 地点-容量锚点。容量比较会同时读取代表容量与 `capacity_details` 中的 MWac/MWp/MWdc，避免把同一光伏项目的 AC/DC 两种口径当成冲突。占位实体「未具名中企」不参与实体重叠判定。
3. **LLM 确认**：候选必须有项目专名、项目公司/开发商、精确场址或信源明示等至少一个身份锚点；同国、同省、同容量本身不足。判断输出分为 `exact_duplicate / same_project_different_event / partial_overlap / distinct`，只有前两类且置信度非 low 才可合并。同一仪式、框架、伙伴或部分地点重叠，但电站数量、总容量或地域组合不同的项目包判为 `partial_overlap`。Prompt 只接收结构化名称、地点、容量明细、开发商、实体和短摘要，不扩入全文。地点和开发商同时明显冲突时，Python 确定性阻止自动及传递合并；不同建设期仍不得合并。
4. **字段仲裁**：合并实体列表、LLM 解冲突字段；容量守卫（名称≥97 自动匹配前若容量差异>20% 降级为 LLM 确认）；代表容量按 `enums.stage_priority` 优先取终态阶段事件。
5. **写库 + 标记**：写规范化三表；回写 `projects.db` 对应记录 `imported_to_s02a=1`。canonical 候选在同国家内跨类别搜索，地点相同或包含的候选优先于仅通用名称高分；低名称分仅在同类、地点一致且容量守卫通过时送模型确认，不自动合并。模型拒绝后至多核验另外两个候选，避免第一个错误候选遮蔽真实历史项目。名称极强匹配，或模型确认名称+地点+容量共同锚定时可复用原 ID；国家+容量本身不足以合并。同阶段既有事件以 fill-if-null 补能源事实。

实体列表优先以 `(entity_id, involvement_type)` 去重；旧格式兼容 `(implementing_entity, subsidiary_name, involvement_type)`。同一集团的不同子公司保留独立主体。旧关系补充 ID 时尽量复用原行，不重复新增。S01B 的实际主体名、集团ID、原文名、身份状态及证据 JSON 透传至 `chinese_entities`。

`publication_status=eligible` 即可流转，`needs_review`字段警告、model_supported_chinese、缺法人ID和Unknown角色不追加门槛。身份标准化待办与参与复核分开。

`publication_status=pending_review` 留在提取库且不标记 imported；确认排除行仅标记已处理，不写业务主表。新事件不能通过 excluded 的 OR 运算排除既有 canonical。已被旧规则误排除的历史项目不自动批量恢复；定向工具 `scripts/oneoff/repair_entity_gate_exclusions.py` 对照更新前备份、核对精确原因与 ID，仅允许在隔离副本应用本次确认的13条。

### 编号生成

`canonical_id` / `event_id` 用 `MAX(CAST(substr(...) AS INTEGER))` 数值取最大尾号 +1（尾号超 9999/99 也不重复）。`canonical_id` 永久不变且不重排；新项目仍按“国家 ISO + 创建时类别码 + 顺序号”生成，类别码保留为历史信息，后续建议类别变化不改号。

### 性能实现要点

- 候选预分组：按 `(country, category, project_stage)` 分组、仅组内两两比较（O(n²)→O(k²)）。
- LLM 确认并行化：`ThreadPoolExecutor(max_workers=3)`；普通高分且中文项目名也达到严格阈值时可直接并入 Union-Find，含“项目包/组合/多座电站”等信号的候选必须进入四态确认，不走高分自动合并。
- LLM 限速重试代替固定 sleep（429 时指数退避）。
- canonical 预加载缓存：启动时一次性载入全部 `canonical_projects` 到内存字典，避免逐项目 SELECT。

## SQLite 数据模型（`data/db/bri_re_database.db`）

四张表 = 三张关系表 + 一张非项目扁平表。类别代码取自 `enums_mapping.json`（经 `bri_enums.category_code()`）。

### canonical_projects（物理工程，唯一）
- PK：`{ISO3}-{CAT}-{NNNN}`，例 `IND-PV-0001`。
- 字段：`project_name(_en)`、`name_en_quality`、`country(_iso)`、`bri_country`、`ldc`、`location`、`location_norm`、`category`、`subcategory`、`excluded`(INTEGER)、`excluded_reason`。
- `excluded=1` 标记非可再生能源等需排除项目（s03 过滤，不进 projects_flat）。
- `subcategory` 仅表达光伏集中式/分布式项目形态；综合能源不再使用光储/其他子类。**只存有证据值**，NULL=无证据（s03 导出层对光伏按 `_default=集中式` 渲染）；能源组合由 `technology_tags_json` 独立表达。

### project_events（里程碑事件）
- PK：`{canonical_id}-{NN}`，例 `IND-PV-0001-01`。
- 字段：`capacity_mw_raw/capacity_mw`、`total_investment_usd_raw/_usd`、`storage_power_mw/storage_energy_mwh/capacity_source`、日期/financing/信源/`project_summary` + 验证字段（`verification_status/confidence/sources/needs_manual_review`）。
- 能源事实列：`generation_sources_json/storage_status/storage_power_mw_raw/storage_energy_mwh_raw/energy_composition_evidence`；发电装机与储能功率始终分列，不相加。

### project_classification_shadow（内部影子快照）

- 每个 canonical 一行，保存发电源并集、聚合储能状态与 MW/MWh、建议类别、技术标签、规则版本、复核原因、来源、人工锁定状态。
- 不被 s03/s04 消费；写入不会改变 `canonical_projects.category/subcategory/id`。
- 存量 schema 使用 `scripts/migrate_add_energy_taxonomy_shadow.py`：默认 dry-run；`--apply` 前 SQLite backup、单事务执行并核对 canonical/event ID 集合不变。
- TX/MF 稀疏专用列（阶段3，仅 TX/MF 事件回填，其余为 NULL）：`voltage_kv/line_length_km/transmission_capacity_mw`（TX）、`production_capacity_value/production_capacity_unit`（MF，单位受控四档见 `enums_mapping.json` 的 `mf_production_unit`）。建表侧 `_init_db()` ALTER 自动补列；存量库用 `scripts/migrate_add_txmf_columns.py`。
- 指标扩展稀疏列（2026-W30）：`pv_capacity_mw`（综合能源项目光伏子项装机，2B-7 回填）、`contract_amount_usd_raw/_usd`（合同金额）、`financing_amount_usd_raw/_usd`（融资额度）——金额来自 s01b 抽取（仅新数据，历史留空），两数值列进 `conflict_fields` LLM 仲裁（raw 短语随 first 不仲裁）。存量库用 `scripts/migrate_add_subcat_amount_columns.py`。

### chinese_entities（中方主体，含金融机构）
- PK：自增整数，FK → `project_events.id`。
- 字段：`implementing_entity(_en)`、`subsidiary_name(_en)`、`entity_en_quality`、`involvement_type`、`subcontract_amount_raw/_amount`、`is_central_soe`。
- 主体及追溯列：`entity_id/entity_name/group_entity_id/raw_entity_name/identity_status/entity_evidence_json`；新列可空，兼容旧库，主键及事件外键不变。

### non_project_records（设备订单 / 一般合作，扁平，一实体一行）
- 不参与去重，与三表体系完全隔离。含 record_type、项目名、国家、类别、容量、阶段、实体、参与方式、金额、融资、信源等。

> 数值字段一律 `*_raw(TEXT,原文)` + REAL（`bri_parse.parse_number` 解析）；`capacity_source` = original/derived/manual/legacy。
