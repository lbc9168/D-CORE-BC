## 已实现功能

### DuplicateMergerTool（去重合并与入库）

五阶段流程：

**1. 数据加载**（Python）
从 `s01b_project_extractor/data/projects.db` 读取 `imported_to_s02a=0` 的未处理记录，并按 `record_type` 分流：
- `record_type == "具体项目"` → 进入后续去重流程
- `record_type != "具体项目"`（设备订单 / 一般合作）→ 直接写入 `non_project_records` 表，跳过去重
- **location 推断**：归组完成后，对 `location` 为空的"具体项目"记录，批量调用 LLM 从项目名中提取省/城市名并回填，提升后续去重 LLM 的判断质量

**2. 候选筛查**（Python）
多信号去重检测（四路信号 OR 逻辑）：
- Signal 1：CN 名称 `token_sort_ratio ≥ 85`
- Signal 2：EN 名称 `token_sort_ratio ≥ 80`
- Signal 3：CN 名称 `partial_ratio ≥ 90`（子串包含）
- Signal 4：容量精确匹配（误差 ≤ 1%，≥ 0.5MW）— 专用于跨语言历史数据安全网
- 实体辅助通道：共有中方实体 + 名称中度相似（≥ 60）

去重阈值（已收紧）：
- 容量误差容忍 ≤ 5%（原10%）
- 豁免容量检查门槛 ≥ 97分（原92）
- 容量检查最小装机 50MW（原0.5MW）
- LLM 确认上下文：增加 `省/地区`、`项目开发商` 字段，新增判断优先级说明

**3. LLM 确认**（Gemini）
确认候选对是否为同一物理项目。

**4. 字段仲裁**（Python + LLM）
合并实体列表、LLM 解决冲突字段。
- **canonical 匹配容量守卫**：名称得分 ≥ 97 自动匹配前，若新项目与已有 canonical 容量差异 > 20% 且有 LLM 可用，降级为 LLM 确认，防止同名不同容量项目错误合并
- **canonical LLM 确认容量来源修复**：改为子查询，优先取 `project_events` 中有值的容量（原 `LIMIT 1` 可能取到无容量值的阶段）。**v2 S2a 起**：读 REAL `capacity_mw`，并按 `enums.stage_priority`（`_stage_order_sql` 生成 SQL CASE）优先取**终态阶段**事件作代表容量。

**5. SQLite 写入 + 标记已导入**
规范化三表结构写入；处理完成后将 `projects.db` 中对应记录标记为 `imported_to_s02a=1`。
- **跨批次同阶段合并**：若新记录与库中已有事件命中同一 `canonical_id + project_stage`，执行完整 LLM 字段合并（等同于批内 `_merge_group`），而非仅追加 `source_links`；无 LLM 时降级为追加 `source_links`（原有行为）

## SQLite 数据模型

数据库路径：`s02a_duplicate_merger/data/db/bri_re_database.db`

四张表（三张关系表 + 一张非项目记录扁平表）：

### non_project_records（设备订单 / 一般合作，扁平，一实体一行）

```
字段: record_type, project_name, country, country_iso, category,
      capacity_mw_raw(TEXT)/capacity_mw(REAL), capacity_details,
      project_stage, implementing_entity, implementing_entity_en, subsidiary_name, subsidiary_name_en,
      involvement_type, subcontract_amount_raw(TEXT)/subcontract_amount(REAL),
      financing_model, financing_model_details,
      source_link, publish_date, additional_remarks, created_at
```

> 此表记录不参与去重，与 canonical_projects 三表体系完全隔离。

### canonical_projects（物理工程，唯一）

```
PK: {ISO3}-{CAT}-{NNNN}  e.g. IND-PV-0001
字段: project_name, project_name_en, name_en_quality, country, country_iso, bri_country, ldc, location, category,
      excluded(INTEGER DEFAULT 0), excluded_reason(TEXT)
```

> **v2 S2a 起**：`excluded=1` 标记非可再生能源等需排除项目（s03 过滤，不进 projects_flat）；实际打标在 S2b 迁移执行。

类别代码（v2 S1 起取自单一可信源 `enums_mapping.json`，经 `bri_enums.category_code()`；原硬编码 `CATEGORY_CODE` 字典已删除。未知类别回退 `UNK` 并记 warning）：

| 中文类别 | 代码 |
|----------|------|
| 光伏 | PV |
| 风电 | WD |
| 水电 | HY |
| 地热及余热 | GT |
| 生物质 | BM |
| 储能 | ES |
| 综合能源 | HB |
| 核电 | NC |
| 火电 | TH |
| 新能源制造业 | MF |
| 输变电建设 | TX |
| 未知 | UNK |

### project_events（里程碑事件）

```
PK: {canonical_id}-{NN}  e.g. IND-PV-0001-01
字段: capacity_mw_raw(TEXT)/capacity_mw(REAL)、total_investment_usd_raw(TEXT)/total_investment_usd(REAL)、
      storage_power_mw(REAL)/storage_energy_mwh(REAL)/capacity_source(TEXT)、
      日期/financing/信源/project_summary + 验证字段(verification_status/confidence/sources/needs_manual_review)
注：已移除 chinese_banks_involved 字段（金融机构改由 chinese_entities 表统一管理）
```

> **v2 S2a 起**：数值字段一律 `*_raw(TEXT,原文)` + REAL（`bri_parse.parse_number` 解析）。`capacity_source`=original/derived/manual/legacy；storage 提取属 v2.1，暂留空。

### chinese_entities（中方主体，含金融机构）

```
PK: 自增整数，FK → project_events.id
字段: implementing_entity, implementing_entity_en, subsidiary_name, subsidiary_name_en,
      entity_en_quality, involvement_type,
      subcontract_amount_raw(TEXT)/subcontract_amount(REAL), is_central_soe
```

involvement_type 枚举：
`BOT/BOOT` / `EPC总承包` / `设计/施工服务方` / `股权投资方` / `设备供应商` / `投融资+EPC` / `融资方` / `Unknown`

## 性能优化（2026-03-22）

### A. 同批次候选预分组（O(n²) → O(k²)）
`_find_duplicate_candidates` 在循环前先按 `(country, category, project_stage)` 分组，
仅在同组内两两比较，避免大量无效跨国/跨类别配对。

### B. LLM 限速重试替代固定 sleep
新增 `_llm_call_with_retry` 包装函数：正常情况下无等待，
遇到 429/ResourceExhausted 限速时指数退避重试（2→4→8…秒，最多重试 5 次）。
原 4 处硬编码 `time.sleep(0.5/1)` 已全部移除。

### D. 同批次高分直接确认（跳过 LLM）
`_deduplicate_projects` 对 `best_score ≥ 97` 的候选对直接并入 Union-Find，
无需调用 LLM（与跨批次 `CANONICAL_AUTO_MATCH_SCORE` 逻辑对称）。

## 2026-03-22 稳定性修复（入库一致性）

- `阶段五 imported 标记` 从“失败仅告警”调整为“失败即抛错”：
  - 若 `extracted_projects.imported_to_s02a=1` 回写失败，流程会显式失败并暴露错误；
  - 避免出现“主库已写入但源库未标记”导致的重复导入和数据不一致。


## 性能优化（2026-03-23）

### E. LLM 确认并行化（ThreadPoolExecutor）
`_deduplicate_projects` 将候选对分流：高分自动确认，其余通过 `ThreadPoolExecutor(max_workers=3)`
并行发送 LLM 请求，全部完成后再统一处理 Union-Find。
预期：30 对串行约 210s → 并行约 70s（3倍提速）；max_workers=3 避免触发 Gemini QPM 限速。

### F. canonical 预加载缓存（N 次 SQL → 1 次）
`_write_to_db` 开头一次性加载全部 `canonical_projects` 到内存字典（按 `(country_iso, category)` 索引），
`_find_or_create_canonical` 直接查内存，新建条目时同步写回缓存。
原来每个项目单独执行一次 `SELECT` 改为启动时一次性加载，数据库越大效果越显著。
