# 阶段一B：AI 提取筛选（s01b_project_extractor）

> 最后更新：2026-08-05（结构化能源事实、严格储能解析、版本化影子分类与 taxonomy eval）

**子项目路径：** `s01b_project_extractor/`

---

## 职责

从 s01a 的 `raw_news.db` 读取原始新闻，用 LLM 做**分阶段结构化提取**，经三层质量校验后写入 `projects.db`，供 s02a 去重合并。

---

## 当前功能

### 分阶段提取链（`stages/orchestrator.py: extract_staged`）

纯 Python orchestrator（无 crewAI），把单次提取拆成 5 个阶段串联：

```
S1 相关性 / 中企门槛 → S2 项目识别（防过度拆分）
  → 逐项目 S4 中方实体（逐字抄原文名）→ S3 金融 → S5 摘要 + 自检纠偏
```

S4 输出的 `implementing_entity` / `subsidiary_name` 为原文逐字抄录；写库前由 `entity_normalize.py` 做确定性查表解析（见"实体解析"节）。

`extract_one` 与生产写库路径 `_process_df` 均委派此 orchestrator，返回结构契约一致。环境变量 `S01B_MERGE_S34` 可将 S3+S4 合并为一次调用（省一次正文重发，默认关；仅对具名项目生效）。各 stage 校验不过独立重试最多 2 次。

### 分阶段供应商路由（`llm/client.py: StageRouter`）

按阶段选 LLM provider，env `S01B_STAGE_PROVIDERS` 配置。**当前默认（写入 .env）= `s3:deepseek,s4:deepseek,s5:deepseek`**——即 S1/S2 用 Gemini（保项目覆盖率），S3/S4/S5 用 DeepSeek。不设该 env = 全 Gemini。三方对比见 `docs/rules_and_plans/eval.md`。

### capacity 确定性解析器（包根 `capacity_parser.py`）

S2 prompt 改"逐字抄录原文数字短语"进 `capacity_mw_raw`；接线在 **`stages/s2_basic.py`**（S2 阶段内调 `parse_capacity_mw`）与**写库路径 `_process_df`**（`tools/project_extractor_tool.py`），做确定性换算：万千瓦×10 / 千瓦÷1000 / GW×1000 / 兆瓦=MW；中文电量单位 兆瓦时/吉瓦时 与 MWh/GWh 同口径拦截；TX/MF 一律 null；产能类（GWh/GW·年/万吨·年）→ null+留 details；解析失败 → null+logging。不变量：`capacity_mw_raw` 非空时为原文逐字短语；`capacity_mw` 为解析值或 null。

### TX/MF 专用指标解析与回填（包根 `txmf_spec_parser.py` + `tools/txmf_backfill.py`）

- **解析器**（纯函数、确定性、无 LLM）：TX 事件出 `voltage_kv`（±N千伏/kV，多值取最大，负排千伏安）、`line_length_km`（公里/千米/km，多值优先「总长/全长」语境）、`transmission_capacity_mw`（输送/输电容量语境 + 万千瓦×10/GW×1000/万千伏安×10/N×M MVA 乘积；MVAr/兆乏/能量单位一律不入）；MF 事件出 `production_capacity_value + production_capacity_unit`（受控四档 GW/年、GWh/年、万吨/年、Unknown，经 `bri_enums` 校验；件数类→Unknown；多个不同产能短语→保守不填进 misses）。数据源优先级 `capacity_details → project_summary → capacity_mw_raw(仅含单位文本时)`；**raw 纯裸数字绝不单独作来源**（历史误解析污染）。
- **回填 CLI**：`uv run --no-sync python -m s01b_project_extractor.tools.txmf_backfill [--db … --apply --out …]`——默认 dry-run（mode=ro）；apply 走 sqlite3 backup API 备份+三重断言+单事务+幂等自检；**fill-if-null 绝不覆盖非空**；范围=未排除 TX/MF canonical 的事件；解析不了且有文本 → misses CSV（`supporting_docs/txmf_backfill_misses_*.csv`，喂阶段 2 T3 或人工）。
- 已接入增量流水线为常设阶段 **2B-5**（见 docs/status/pipeline.md）。

### 能源事实、严格储能回填与影子分类（`energy_taxonomy.py` + 两个 tools）

- **S2 事实契约**：除 legacy `Category` 外输出 `Generation Sources`、`Storage Status`、储能 MW/MWh 原文短语与能源构成证据；Python 后处理校验受控发电源/状态并确定性换算数值。模型不输出建议类别或最终标签。
- **严格储能解析器**（`energy_taxonomy.extract_energy_facts`）：只有明确储能上下文才认定 confirmed；年发电量、工厂 GWh/年产能、设备出口、仅出现 battery 字样、预留/拟配/可选配置均不会写 confirmed 容量。
- **光伏子项解析器**（`extract_pv_capacity`）：仅综合能源(HB)项目用——"光伏/PV/photovoltaic/solar + N"按单位换算 MW/兆瓦、GW/吉瓦×1000、万千瓦×10、kW/kWp/千瓦÷1000（能量单位 兆瓦时/千瓦时/吉瓦时 负向排除）→ `pv_capacity_mw`（纯光伏项目 capacity_mw 即光伏容量，不重复）。**不改 prompt**：S2 prompt 已强制混合项目子项明细写入 Capacity Details。
- **确定性策略 v1**：发电源 0+confirmed 储能→储能；1 个发电源→对应类别；2 个以上→综合能源；储能不计入发电源数量。仅 confirmed 生成组合标签与“含储能”。事件聚合取发电源并集，状态优先级 confirmed > planned > optional > unclear > not_mentioned。
- **2B-7 回填**：保留光伏集中式/分布式形态判断，但停止新增 `综合能源/光储`；已有值不回滚。
- **2B-8 影子工具**：`python -m s01b_project_extractor.tools.energy_taxonomy_shadow --db … [--apply] [--out-csv … --out-json …]`。默认全库只读；apply 仅 upsert `project_classification_shadow`，人工锁定行不覆盖，正式 category/subcategory/id 不变。
- **Eval**：gold 项目可选增加 `generation_sources/storage_status/storage_power_mw/storage_energy_mwh`；独立报告集合 P/R/F1、状态准确率、MW/MWh ±5% 与派生类别准确率，不改变旧 weighted score。

### 提取流程要点

- **Python 端预筛**：先用关键词（光伏/风电/MW 等）快速过滤，节省 API 调用。
- **增量去重**：每次运行前从 `projects.db` + `review.db` 预加载已处理 URL 跳过重复（并发安全：原子检查 + 占位）。
- **发布日期前向填充**：并发前按顺序预计算，URL 日期不可解析时沿用上一条有效发布日期。
- **两层并发**：批次级 4 并发（`run_bulk_extract` 的 `max_extract_workers`）× 批内文章 24 并发（`_process_df` 的 `max_workers`，v2.1 C1 提速后由 4 上调），无逐文章 sleep。
- **重试与 503 设计**：AI 调用失败指数退避重试最多 3 次；重试耗尽的失败篇写 `discarded_records` 但 **source_link 留空**——增量去重只认三表中非空 source_link，故重跑 `run_bulk_extract` 会自动重试失败篇（503 风暴期反复重跑直到"放弃"计数归零）。
- **三路写入**：`valid_project` → `extracted_projects`；`no_chinese_participation` / `irrelevant` → `review.db`。
- **未具名中企（chinese_unnamed）**：项目信息正常入库，实体写占位（`未具名中企` / `is_unnamed_placeholder=1`），同时在 `review.db/review_queue` 写一条 `reason_type="unnamed_entity"` 待复核条目。
- **S2 中排除决策记录**：S2 `in_scope=false` 时写 `excluded=1, exclude_source='extraction'`（确保所有排除决策留有记录）。
- **S1 prompt 排除规则**（`prompts/s1_relevance.py`）：矿产/化肥/化工/冶金/建材产品本身不录入；制造业限新能源装备/材料；绿氢须明确可再生电来源种类，仅提「绿氢」无种类 → 排除。
- **S2 prompt 规则**（`prompts/s2_basic.py`）：综合能源(HB)每子项须有发电/储能 + MW/MWh 计量；绿氢按绿电来源种类分类（光伏→PV/风电→WD/水电→HY），来源未明确 → `in_scope=false, Category=Unknown`。
- **S2 业主判定规则**（`prompts/s2_basic.py`「业主判定」节）：`Project Developer` 证据白名单制——仅当原文出现 显式指认/投资建设/EPC发包方/股权持有收购/特许经营权人/PPA卖电方 之一才填；承包商/设备商/融资机构/**购电方**/审批政府不得填（例外：制造业厂主自建、自有电站售电）；无证据**留空**；JV 拆填各合资方（`;` 分隔，只写公司名，禁括注/股比）；同时输出 `Project Developer Evidence` 原文短语。
- **S2 收录边界规则**（`prompts/s1_relevance.py` + `prompts/s2_basic.py`）：绿氢/制造业/矿产伴生光储的收录判定细则已补入；"缅甸批量招标不拆条、一期二期分条"等边界规则明确写入 S2 prompt。
- **S5 纠偏覆盖 involvement_type**（`stages/s5_summary.py: apply_s5`）：`apply_s5` 的 `valid` 枚举集与 `field_map` 扩展了第三字段 `involvement_type`，使 S5 自检纠偏同时覆盖 status / category / involvement_type。⚠️ 已知局限：一项目多实体不同角色时，单值覆盖可能改错正确实体。

### 翻译入口行为（`tools/project_extractor_tool.py: _resolve_entity_en / _resolve_developer_en`）

- **ASCII 直通**：`_resolve_entity_en(cn)` 入口若输入已是纯 ASCII 字符串，直接返回原值——不查缓存、不调 LLM（英文原名保留原样，不经翻译改写）。
- **developer 拆串翻译**：`_resolve_developer_en` 将 `project_developer` 字段按 `DEV_SEP_RE`（`[;；、，,/]`）拆分，对每个部件分别调用 `_resolve_entity_en` 翻译，结果以 `'; '` 拼回；两处 developer 调用点均接入此逻辑。
- **缓存写入守卫**：多公司串（含分隔符）或超长键（>30 字）翻译后**不写缓存**，防止垃圾键积累。
- **已知取舍**：缓存中已有 ~30 个 value-added 英文键（如 `"Canadian Solar"→"Canadian Solar Inc."`）属 ASCII，被直通后其增量后缀（"Inc."/"Ltd."）不再追加——符合「缩写为主」口径，已知接受。

### 主库实体回填 CLI（`tools/entity_reparse_maindb.py`）

对主库 `chinese_entities` 全量重解析并回填（使用当前 entity_normalize 逻辑 + company_hierarchy_v2.json）：


> **Apply 后部署顺序（硬约束，详见 `docs/status/pipeline.md` 约束5）：en_backfill → run_export(s03) → 部署**

### 缓存审计 CLI（`tools/cache_hygiene.py`）

六规则扫描 `company_name_cache.json`：R1 键含分隔符（多公司串/头衔串）、R2 键含头衔职位词、R3 键为占位泛指短语、R4 键超长(>30字)、R5 值含中文、R6 值含换行/超长/括注噪声；`verified=true` 全部豁免。支持 `--corrections CSV` 通道（`cn,en,en_abbr,verified,source`）修改/新增键值。

### 实体解析两步（S4 逐字抄 + 确定性查表）

#### 步骤一：S4 prompt 逐字抄录

S4 prompt 删除所有层级表注入；`implementing_entity` / `subsidiary_name` 均填**原文逐字抄录**（subsidiary 无子公司记录则留空）。

#### 步骤二：entity_normalize 纯查表三层（`stages/entity_normalize.py`）

写库前对 implementing_entity / subsidiary_name 按三层顺序解析：
1. **精确名匹配**（子公司名/集团名/别名）→ 返回 canonical 集团名
2. **别名匹配**（v2 JSON 中 `aliases` 列表）→ 返回 canonical 集团名
3. **去尾缀归一化**（剥"有限公司/集团/股份"等后缀再精确匹配）→ 返回 canonical 集团名

未命中 → **透传原文 + logging**（不做包含匹配，不猜测）。`is_central_soe` 由登记册（v2 JSON `is_central_soe` 字段）推导；未命中时沿旧逻辑（soe.md 兜底）。

知识库：`supporting_docs/company_hierarchy_v2.json`（**151 组 / 441 子 / 142 集团别名 / 48 央企组**，2026-07-09 实测，含 2026Q3 T3 补录；v2 schema，懒加载缓存；由 `supporting_docs/build_hierarchy_v2.py` 生成）+ `supporting_docs/soe.md`（兜底）。

> 旧文件 `company_hierarchy.json`（17 组）仍在目录，已被 v2 版本取代，不再使用。

### Layer 0：确定性非能源兜底（`guardrails/nonenergy_check.py`）

写库前强制执行，不依赖 LLM：

- `check_nonenergy(name, summary, category, capacity_mw, capacity_details) -> str | None`：发电语义词白名单放行（发电/电站/光伏/风电/水电/储能/地热/太阳能/并网/装机/MW 等，含输变电语义 电网/千伏/供电 与制造语义 多晶硅/bipv；核电无单独词条，但「核电站」命中「电站」亦被保护）+ 黑名单拦截（天然气/油田/LNG/矿业/化工/海水淡化等，含民用基建词 灌溉/排水/水渠/道路/公路/机场/铁路/桥梁/体育场馆/医院/学校/教学楼），返回排除理由字符串或 None。
- 容量吨/年守卫（`capacity_is_tonnage`）：容量字段以吨/年计时 `capacity_mw` 置 NULL，不做 ÷1000 启发式转换，原文保留于 `capacity_mw_raw`。
- 绿氢/电解守卫：名称或摘要含绿氢/电解词，若未同时提供「绿电来源种类（光伏/风电/水电等）+ 明确装机容量 (>0 MW)」→ 排除（用户规则 2026-07-02）。
- 吨/年产能判非发电（Rule 3）：容量仅以吨/年计、名称+摘要无发电语义 → 排除；**豁免类别 新能源制造业/生物质/地热及余热**（垃圾焚烧发电等按处理吨量计属正常口径），且名称无「发电」但摘要含「发电/绿色电力」者放行；只查 name+summary，不查 capacity_details（避免辅助供电诱饵词误放行）。
- Unknown 类别兜底（Rule 4）：category=Unknown 时，项目名为空 → 排除；或名称+摘要+容量明细**全文**无任何发电语义且无装机数值 → 排除（拦词表列不全的长尾民用项目：别墅/食品厂/度假村/办公楼等；与规则 2 相反此处查全文并认装机，偏保守）。
- 命中时写 `excluded=1, exclude_source='deterministic_guard'`，项目仍落 `extracted_projects` 供追溯，对 s02a 不可见。
- **Layer 0 接入点**：确定性守卫在写库前调用，改写为 `excluded=1, exclude_source='deterministic_guard'`；项目仍落 `extracted_projects` 供追溯，但对 s02a 不可见。

### Layer 0：确定性业主守卫（`guardrails/developer_check.py`）

写库前对 `valid_project` 行执行 `clean_developer(developer, entities, category)`，不依赖 LLM：

- developer 拆串后各部件与**同事件中方实体**（母/子公司名双向互含，≥3 字）重名时按实体角色处置：纯承包角色（EPC总承包 / 设计·施工服务方）→ **剔除**；设备供应商 → 剔除但**豁免 `category=新能源制造业`**（厂主=设备商自建）；投资类角色（股权投资方 / 投融资+EPC / BOT/BOOT）**一票保留**；融资方 / 一体化方案提供商等无抽样证据角色保守保留。
- 剔除发生在英文翻译之前（被剔部件不再耗翻译调用）；剔除明细记 `logger.info`。unnamed 路径无实体角色，不适用。
- 依据：2026-07-04 验证抽样（`supporting_docs/developer_sampling_verdicts_20260704.csv`）——重名-纯EPC 组 6/6 全错、重名-设备商组多数错。

| contract_amount_usd_raw / _usd | 合同金额（EPC/承包合同额）：逐字原文 + 解析值(REAL,百万美元)；prompt B.5 归属规则防与投资额/融资额互相污染；2026-07 起新数据抽取，历史留空 |
| financing_amount_usd_raw / _usd | 融资额度（贷款/授信/银团）：逐字原文 + 解析值(REAL,百万美元)；三类金额概念不互斥可同存；2026-07 起新数据抽取，历史留空 |
| planned_start_date / planned_complete_date | 开工/竣工日期 |
| financing_model / _details | 融资模式及详情 |
| source_link / publish_date | 原文链接 / 发布日期 |
| project_summary | 2–3 句事实摘要（供 semantic_checks 交叉验证） |
| needs_review | format_checks 失败时置 1（ALTER TABLE 幂等加列） |
| is_unnamed_placeholder | 实体为占位"未具名中企"时为 1 |
| batch_id / imported_to_s02a | 来源批次 / 是否已被 s02a 导入（增量标志） |

> 数值字段统一 `*_raw(TEXT,原文)` + REAL（由根 `bri_parse.parse_number` 解析）；枚举取自根 `enums_mapping.json`（经 `bri_enums`）。

## 如何运行

```bash
uv --project s01b_project_extractor sync
```

### 非能源回溯清扫（历史数据治本）

```bash
cd s01b_project_extractor

# Dry-run：输出 CSV 报告，不修改数据库
uv run sweep_nonenergy --db data/projects.db --out /path/to/dryrun.csv

# Apply（GATED）：先备份 .bak.YYYYMMDD_HHMMSS，再批量 excluded=1
uv run sweep_nonenergy --db data/projects.db --apply
```

> `--apply` 执行前须用户复看 dry-run CSV，确认无误后再操作。Apply 后需重跑 s02a → s03 → 部署。

### 主库非能源回填（原地回填，不重建 s02a）

```bash
cd s01b_project_extractor

# Dry-run：对主库 canonical_projects（聚合各自 events 后判定）输出 CSV，不写库
uv run sweep_nonenergy_maindb --out /path/to/dryrun.csv   # --db 默认指向主库

# Apply（GATED）：先备份主库 .bak.YYYYMMDD_HHMMSS，再事务批量 excluded=1（写 excluded_reason）
uv run sweep_nonenergy_maindb --apply
```

> 与 `sweep_nonenergy` 同一套护栏规则（`guardrails/nonenergy_check.py`），粒度为 canonical：
> 任一事件含发电语义即保护整个项目。Apply 后需重跑 s03 → 部署（不重跑 s02a）。

### 缓存审计（历史垃圾键清理）

```bash
cd s01b_project_extractor

# Dry-run：扫描 company_name_cache.json，输出清理候选报告
uv run cache_fix \
  --cache <路径>/supporting_docs/company_name_cache.json \
  --corrections <路径>/supporting_docs/cache_corrections/2026-07-04-hard-errors.csv \
  --out /path/to/report.csv

# Apply（GATED）：用户复看报告后执行
uv run cache_fix --cache ... --corrections ... --apply
```

种子 corrections 文件：`supporting_docs/cache_corrections/2026-07-04-hard-errors.csv`（4 条已知错译，`verified=false`，需核实后改为 `true` 再 apply）。
