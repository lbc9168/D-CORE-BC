## 当前功能

### 实体别名候选（`entity_normalizer.py`，只读）

1. 以 SQLite `mode=ro` 加载 `chinese_entities.implementing_entity` 的不同值和频次。
2. 用 token/partial/subsequence 三个信号发现相似名称对。
3. 排除登记册已经同时解决的名称对，输出 `entity_alias_suggestions_*.csv`。
4. CSV 预留 `review_relationship`、`approved_canonical` 和 `review_notes`，人工需区分 `same_legal_entity`、`subsidiary_of`、`unrelated`、`uncertain`。

该入口不调用 LLM、不构造 Union-Find 传递闭包、不更新主库。旧 `_update_db` 入口会直接抛错。批准结果先维护 `company_hierarchy_v4.json`（或经审批新增文件），再通过 S01B `entity_intake refresh` 定向重判源行并经S02A重放。`entity_reparse_maindb`仅保留旧格式名称修复兼容，新主体ID格式主库禁止其apply。

### 实体恢复与保守去重工具

- `recover_entities`：一次性恢复工具；历史行按稳定 ID 从基线库恢复，指定日期增量行从 `projects.db` 重建，默认 dry-run，apply 前 SQLite 快照并在单事务写入。
- `deduplicate_entities`：仅合并 `(event_id, implementing_entity, subsidiary_name, involvement_type)` 全部相同且其他业务字段无冲突的重复；金额等非空值冲突时只报告、不删除。

### 共享查表引擎（`company_lookup.py`）

developer 归一与 EN 回填共用的三层查找：① 根目录 `developer_registry.json`（登记册：canonical_cn/canonical_en/aliases，含跨语言别名；Pydantic 载入校验+别名全册冲突断言）→ ② 中文部件续查 `supporting_docs/company_hierarchy_v4.json`（只读；变体→该实体自身规范名 `legal_full_name_cn`，绝不上卷母公司；context_required_names 不参与全局映射）→ ③ 透传+miss 记录。`build_index()/lookup(part, index)/collect_misses(index)`。

`group_only_aliases` 只证明集团归属，不视为某具体法人的同名；`disputed_aliases/review_names` 不参与自动法律主体归一；`context_required_names` 的通用裸称不作全局名称映射。两份名录保持独立，Developer 字段是否成立由 S01B 的本项目原文证据决定，lookup 仅规范已经存在的名称，不生成角色。

### developer 归一化（`developer_normalizer.py`）

`run(db_path=None, preview=False, apply=False, use_registry=True)`：整值垃圾占位统一 `Unknown`；**登记册确定性查表前置**——中文与纯 ASCII 部件都过 `lookup()`，命中且规范名≠原文直接进映射（跨语言归一如 `Masdar→阿布扎比未来能源公司` 由此实现）；LLM 只处理未命中部件的候选对，确认结果**降级为登记册补录建议 CSV**（`supporting_docs/developer_registry_suggestions_*.csv`，不写库），miss 出 `developer_norm_misses_*.csv`。该 LLM 路由为 GPT-6 Luna、`reasoning_effort=medium`（`S02B_DEVELOPER_MODEL/EFFORT`），因为它要区分同一法人写法与母子公司/联合体关系。`use_registry=False`=旧口径 100% 等价（对照/回退位）。apply 前 `.bak`、单事务、幂等（重跑 0 变更）。裸跑不调 LLM、不写库。

`project_developer_en` 不在本工具处理范围——归一后由 `backfill_entity_en` 统一重算（EN 单一写入方）。

剩余英文名翻译使用 GPT-6 Luna、`reasoning_effort=low`（`S02B_TRANSLATE_MODEL/EFFORT`）：属于受约束的翻译任务，名称缓存优先，批内结果还会校验是否残留中文。地点归一使用 GPT-6 Luna、`reasoning_effort=medium`（`S02B_LOCATION_MODEL/EFFORT`）：它判断音译/拼写变体是否为同一地点，确认边会通过 Union-Find 传递合并，因此保守处理更重要。S02A 批内地点归一也使用 medium。

### 英文名回填（`en_backfill.py`）

`main()`（CLI 入口）：三档来源优先级 **registry `canonical_en` > 缓存 en_abbr > 缓存 en**，回填主库三列（`chinese_entities.implementing_entity_en`、`chinese_entities.subsidiary_name_en`、`project_events.project_developer_en`）与 `projects.db` 同名三列。registry 档缺省开启（CLI `--no-registry` / `run_backfill(use_registry=False)` 可回退）；**纯 ASCII 值也查册**（册命中直填 canonical_en），未命中才维持 ascii_skip。

- hit（含 hit_registry/hit_multi_registry）且 diff → update；miss / 未命中 ascii 值 / Unknown → 只记录，不改动。
- apply 前每库各自 `.bak`；dry-run 默认（无 `--apply` 则不写库）。
- `--out CSV` 导出明细（列：`status`（hit/hit_multi/miss/partial_miss）+ `action`（update/report_only））；ASCII/Unknown 行不出现在 CSV；miss 清单即 campaign 候选池。

### 剩余名称翻译回填（`en_translate_residual.py`，流水线 2B-6）

`run_residual_translate(db_path, apply=False, ...)`：处理 en_backfill 之后仍未翻译的长尾中文名。扫描主库三对名称列中**挂 excluded=0 项目、`*_en` 空或含中文**的值（占位/纯 ASCII 跳过）；逐部件四层解析 **registry canonical_en > 主缓存 en_abbr/en > 残余缓存 > LLM 批翻**（GPT-6 Luna、`reasoning_effort=low`，20 名/批；`S02B_TRANSLATE_MODEL/EFFORT`）。新翻译写独立缓存 `supporting_docs/residual_translation_cache.json`（source=llm_auto、verified=false，并记录模型与 effort；与人工核实的主缓存隔离；registry 后续入册可自动压过）并出新增翻译 CSV（utf-8-sig，供抽检/喂季度 campaign）。落库 **fill-if-null**（只填 en 空/含中文行，绝不覆盖有效英文；`.bak` + 事务 executemany）。翻译失败或结果含中文：不缓存不落库，下轮自动重试；季度增量只有新 miss 才产生 LLM 调用。

### 容量与规格回填（S01B tools，由流水线 S02B 调用）

`txmf_backfill` 和 `storage_subcat_backfill` 仍按 fill-if-null、备份、事务和幂等检查运行。两者消费事件关联的 `entity_evidence_json.withheld_capacity_fields`，明确拒绝的字段不能从摘要/详情自动重生；其他字段独立补值。安全修复后在同一事务更新 `field_validation` 当前状态为 `repaired`，之前状态保存到 `field_validation_audit`，原始提取与警告仍可追溯。旧记录无该元数据时保留既有回填行为。

### 地点归一化（`location_normalizer.py`）

- `normalize_locations` 写 `canonical_projects.location_norm`（**只增列、不动原 `location`**；下游 s03/s04 当前不消费 → 零功能影响、可逆）。
- LLM 确认由 GPT-6 Luna 执行，`reasoning_effort=medium`；配置项 `S02B_LOCATION_MODEL/EFFORT`。
- 匹配规则在根 `bri_location.py`：多地名串排除、partial 长度比守卫、方向签名守卫（前缀/复合中部/后缀）、positional 收紧，防止 union-find 把共享岛名/后缀的不同省跨省级联误并。

## 如何运行

```bash
cd s02b_entity_normalizer
uv sync
uv run normalize_entities                # 只读输出实体别名候选 CSV
uv run normalize_entities --db /path/to/custom.db --out /path/to/suggestions.csv

# 历史实体恢复（默认 dry-run；一次性/明确 campaign 使用）
uv run recover_entities --db <主库> --baseline <基线库> --projects-db <projects.db> \
  --start-date YYYY-MM-DD --end-date YYYY-MM-DD --out /path/to/recovery.csv
# 复核计划后在同一命令末尾加 --apply

# 真正重复行清理（默认 dry-run；冲突组保留）
uv run deduplicate_entities --db <主库> --out /path/to/dedup.csv
# 复核报告后在同一命令末尾加 --apply

# developer 归一（裸跑=preview，不写库；确认后加 --apply，GATED）
uv run normalize_developers           # 等同 --preview：展示候选对，不调 LLM，不写库
uv run normalize_developers --apply   # 落库（调 LLM + .bak + executemany）

# 英文名回填（dry-run 默认；apply GATED，建议缓存审计+corrections 后再跑）
uv run backfill_entity_en \
  --db <主库路径>/bri_re_database.db \
  --projects-db <s01b路径>/data/projects.db \
  --cache <路径>/supporting_docs/company_name_cache.json \
  --out /path/to/dryrun.csv
# 复看 CSV 后：
uv run backfill_entity_en ... --apply

# 剩余名称翻译回填（裸跑=preview 只报缺口计数；--apply 调 LLM 翻译+写缓存+回填）
uv run translate_residual_en                 # preview：待翻值/缺口部件计数
uv run translate_residual_en --apply         # 翻译并落库（.bak + fill-if-null）
uv run translate_residual_en --out /path/to/new_translations.csv --apply
```

## 输入 / 输出

- **输入**：
  - `../s02a_duplicate_merger/data/db/bri_re_database.db`（`chinese_entities` + `canonical_projects` + `project_events`）。
  - `../s01b_project_extractor/data/projects.db`（`backfill_entity_en` 同时回填此库的三列）。
  - `supporting_docs/company_name_cache.json`（`backfill_entity_en` 的英文名来源，en_abbr 优先口径）。
  - `supporting_docs/residual_translation_cache.json`（`translate_residual_en` 的残余翻译缓存，首跑自动创建）。
- **输出**：实体候选步骤只写审核 CSV、不改 SQLite；其他子步骤按各自门禁更新 `project_developer`、`location_norm` 与英文名三列。

## 与 s01b 的分工

| 场景 | 处理方 |
|------|--------|
| 实体在 `company_hierarchy_v4.json` 中有条目 | s01b 提取时确定性写集团规范名，并把具体主体写 `subsidiary_name` |
| 实体不在登记册中 | 原样透传；s02b 只读生成补录建议，不自动改库 |
| 已入库数据的名称修正 | 登记册更新后，源库`entity_intake refresh` dry-run/apply → S02A重放；缺历史证据单独核实 |

## 关键依赖与约束

- 实体建议依赖 rapidfuzz，但不依赖模型调用。`run()` 被 pipeline 以函数参数调用时不解析 `sys.argv`。
- 母公司与子公司不是 alias；同一法律实体的全称/简称/旧称才可登记为 alias。禁止用模糊名称相似度直接决定 canonical。
- 地点归一的合并质量依赖 LLM：音译近似的不同省可能偶发误并。`location_norm` 当前不喂下游，属软信息；后续若让 s03/s04 消费需先人工抽查。
