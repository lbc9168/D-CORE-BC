## 关键排序逻辑：先造尺子（P0），再改东西

v2.1 核心卖点是"提升正确率"，但 A.0 把单 prompt 拆成多 agent 是双刃剑（可能更准、也可能引入新错且更贵）。**没有评测集就无法判断每次改动是进步还是退步**，只能凭感觉（change-suggestion A.6 同此意）。故 P0 最先做，作为 P1 及之后所有改动的度量基准。

## P1 实施计划须在 P0 基线之后再写（重要）

P1 的**设计**（架构：分阶段、按字段拆、可配置 client）已定且不依赖 P0 数字；但 P1 的**实施计划**应在 **P0 跑出当前提取器基线后**再落，由 P0 结果驱动：
1. 按 P0 字段级弱项报告**排 P1 优先级**（哪个阶段/字段最差就先补，不平均用力）。
2. 用 P0 在 gold set 上 **A/B：Gemini vs deepseek-v4-lite**，再最终确认 P1 的模型选型（万一 deepseek 更差就改）。
3. 用 P0 验证 P1 的**增量切分**（先切 S1+S2，run_eval 涨了再推进）。
4. 校准 A.3 容量反推系数、A.1/A.2 分类规则是否真把已知错例修对。
P0 用两次：先作基线（塑造 P1 计划），P1 改完后再跑（逐字段证明进步 + 回归门）。
→ 故**勿在 P0 基线出来前冻结 P1 实施计划**。

## 各子项目流程

每个子项目独立走：brainstorm（设计）→ spec 落 `docs/superpowers/specs/` → writing-plans 出实施计划 `docs/rules_and_plans/sessions/` → 执行（建议各开干净会话）。P0 设计已完成。
