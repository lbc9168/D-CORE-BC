## A 类：AI 提取与分类规则的准确率

> 目标：从源头（s01b 提取）降低错误率。对应你反馈"数据错误率比想象高""需要提升正确率的路径"。

### A.0 把"单一巨型 prompt"拆成多 agent / 多阶段（对应开头总纲）

**现状**：`s01b/.../project_extractor_tool.py` 的 `_build_prompt()`（L362-519）是一个 ~160 行的巨型 prompt，让一次 LLM 调用同时做：判定中企参与 → 剔除无关 → 分类 → 抽容量/日期/金融/实体 → 写摘要。任务越多，单点出错概率越高，且无法针对薄弱环节单独加强。

**建议（分阶段抽取，pipeline 内串联）**：

- **Agent 1｜相关性与中企参与判定**：只输出 `valid/no_chinese/irrelevant` + reasoning。规则集中、可单独调阈值。
- **Agent 2｜项目基本信息抽取**：项目名、国家、地点、类别、阶段、容量。
- **Agent 3｜金融信息抽取**：投资额、融资模式、融资方、分包额、投融资日期（你反馈金融信息单独 agent）。
- **Agent 4｜中方实体与参与方式抽取**：实体层级 + involvement_type（可与"设备供应商细分"agent 合并，见 A.5）。
- **Agent 5｜摘要 + 自检**：基于前面结果生成 project_summary，并交叉验证（即现有 Layer 2 semantic_checks 思路）。

**实现要点**：

- 现有三层 Guardrail（format/semantic/batch）可保留，作为每个 agent 输出后的校验器。
- 代价是 token/调用数上升（每篇文章多次调用）。可用"先 Agent1 过滤，只有 valid 才进入 2-5"来控成本——这与现有 Python 预筛（L671-674）思路一致。
- **过渡方案**（低成本）：先不拆进程，只把 prompt 内部按"任务块"拆成多次 `generate_content` 调用并各自校验，验证收益后再上 crewAI 多 agent。

### A.1 垃圾发电 = 生物质（数据筛选 #12）

**现状**：prompt 的 Category 列表（L505-509）有"生物质"，但**没有任何一句**把"垃圾发电/垃圾焚烧发电/固废发电/沼气发电"映射到生物质（THA-HB-0001 因此被错分）。

**建议**：在 `_build_prompt` 的 Category 规则里新增明确条目：

> "垃圾发电 / 垃圾焚烧发电 / 生活垃圾发电 / 固废发电 / 沼气发电 / 填埋气发电 → 一律归类为『生物质』。"

并补充一两个反例（如"焚烧炉余热回收"应判生物质而非余热）。同时在 `scripts/clean_historical_data.py` 的 category 映射表里补这些词，做一次存量修复。

### A.2 数据中心项目须 RE 供电才算（数据筛选 #6）

**现状**：prompt 的"内容筛选规则"（L382-401）只排除学校/医院/机场等用电户，**未提数据中心**。

**建议**：在筛选规则新增：

> "数据中心 / IDC / 算力中心 项目：除非新闻明确说明该项目由可再生能源（自建光伏/风电/绿电 PPA 等）供电，否则按『irrelevant』剔除；若明确 RE 供电，则按其配套的发电类型分类。"

### A.3 装机容量计算：只有年发电量时反推（数据筛选 #8）

**现状**：prompt 的容量规则（L403-411）只让"填数字"，没有"只有年发电量、无装机容量时如何处理"。这类项目目前 `Capacity (MW)` 留空 → 到前端因"应有容量却为 null"被**整条剔除**（见 check-record §3.6 #3）→ 项目直接消失。

**建议（两层）**：

1. **prompt 增加换算指引**：
   
   > "若新闻只给出年发电量（如『年发电量 4.5 亿千瓦时』）而无装机容量，按该能源类型典型容量系数反推装机容量，填入 Capacity (MW) 并在 Capacity Details 注明『由年发电量X反推，按系数Y』。典型容量系数参考：光伏 ~17%、陆上风电 ~25%、海上风电 ~40%、水电 ~45%（小水电~50%）。"
   - 公式：`装机MW ≈ 年发电量(MWh) / (8760 × 容量系数)`。
2. **数据可信度标记**：新增字段 `capacity_source`（见 §C.1），区分"原文直接给出 / 由年发电量反推 / 人工核定"，避免反推值被当成硬数据。

### A.4 储能容量单列（数据筛选 #9）

见 §C.2（属 schema 改动，放 C 类统一说明）。prompt 侧需同步：综合能源/储能项目要分别输出"发电装机 MW"与"储能容量 MW/MWh"，不再都塞进 Capacity Details 文本。

### A.5 设备供应商主/次设备细分（数据筛选 #2、#13）

**现状**：involvement_type 里有"设备供应商"，但不区分**主要设备 vs 非主要设备**，也不记录"供了什么设备"。

**建议（独立 agent + 知识表）**：

1. 新建 `supporting_docs/main_equipment.json`，按项目类型列出主要设备清单，例如：
   
   ```json
   {
     "光伏": ["组件", "逆变器", "支架(主要时)"],
     "风电": ["风机/机组", "叶片", "塔筒(主要时)", "齿轮箱"],
     "水电": ["水轮机", "发电机", "闸门(主要时)"],
     "输变电建设": ["变压器", "GIS", "换流阀"]
   }
   ```
2. 新增"设备分类 agent"：输入(项目类别, 新闻中提到的中企供货内容) → 输出 `equipment_role ∈ {主要设备, 非主要设备, 未提及}` + `equipment_items`（具体设备名）。
3. schema 在 `chinese_entities` 增 `equipment_role`、`equipment_items` 两列（见 §C）。
4. 关于"变电站/升压站再细分"：建议先用上面的 equipment_items 自由记录，**暂不**在 category 里硬拆出子类（避免枚举爆炸）；待数据量够、需求明确再做专业细分（你也提到要查专业文献，属调研项，先记 TODO）。

### A.6 提升整体正确率的可操作路径（数据筛选 #5）

- **建立"金标准抽样集"**：人工标注 100~200 条作为 ground truth，每次改 prompt/模型后跑一遍算字段级准确率，量化每次改动是进步还是退步（否则只能凭感觉）。
- **升级模型用于"高价值字段"**：容量/金融/分类等关键字段可用更强模型（如 s02a 已在用的 gemini-3 系列），低价值字段用 lite，平衡成本与质量。
- **把 review.db 利用起来**：被剔除/无中企的记录定期人工抽查，反推 prompt 的漏判/误判模式。

## B 类：去重与"同一性"识别精度（数据筛选 #3）

> 目标：让"音译地名不同/中英文混写/跨批次"的同一项目能正确合并；同一实体能正确归并。

### B.1 地点归一化（达瓦德密 = 达旺德米）

**现状**：`s02a/.../duplicate_merger_tool.py` 的 `_infer_location_from_name`（L426-478）只对**空** location 用 AI 回填，不统一音译变体；候选预分组（L506-508）按 `(country, category, project_stage)` 不含 location；是否同地全交给 `_llm_confirm` 的世界知识。

**建议**：

1. **新增 location 规范化步骤**（在 s02a 去重前，或独立成 s02b 的一部分）：对同一国家内的所有 location，用"AI + 模糊匹配"聚类音译变体，产出 `{location 变体 → 规范地名(英文/标准译名)}` 映射，回写 canonical/event。机制完全可复用现有 `s02b entity_normalizer.py` 的"三信号候选 + LLM 批量确认 + Union-Find"框架，把对象从"公司名"换成"地名"。
2. **可选增强：地理编码**。对规范地名做一次 geocoding（如离线 GeoNames / Natural Earth 质心），存经纬度。则去重时可用"同国 + 距离<阈值"作为硬锚点，比纯名称稳得多，也能直接复用到 s04 省级地图。

### B.2 跨语言/跨批次漏合并（雪兰莪案例）

**现状**：批内只在同 `project_stage` 组内比对（L510-514）；跨阶段、跨批次靠 `_find_or_create_canonical`（L943-1061）的名称模糊匹配兜底。名称差异大就漏挂同一 canonical。

**建议**：

1. **候选分组去掉 project_stage 维度**：改为按 `(country, category)` 分组，让不同阶段的同一项目也能成为去重候选（同一性由 LLM 判断"是否同一物理工程"，而非"同一阶段"——本来 schema 就支持一项目多阶段事件）。这能直接修复"签约/竣工分属不同组而漏配"的情况。
2. **引入容量 + 地点的硬锚点**（依赖 §C.1 数值化、§B.1 地点规范化）：在名称模糊分低时，用"同国 + 容量接近 + 同规范地名"作为强信号送 LLM，弥补跨语言名称分极低的问题（现有 Signal 4 已是雏形，但只用容量、且容量是 TEXT 不可靠）。
3. **canonical 匹配也纳入地点**：`_find_or_create_canonical` 目前只比名称四元组（L982-989），建议把规范地名/容量也纳入打分或 LLM 上下文。

### B.3 实体归一化的副作用（check-record §3.3 #1）

`s02b entity_normalizer._update_db` 用母公司学到的映射无差别改 `subsidiary_name`，建议拆成两套映射分别处理，或对 subsidiary 改写加二次确认。

## C 类：字段与数据结构（schema）设计

> 这是 B、D 的地基，**建议最先做**。涉及 s01b → s02a → s03 三处 schema 同步改动 + 一次存量迁移。

### C.1 数值字段真正数值化（check-record 系统性隐患 #1）

**现状**：容量、投资额、分包额在 s01b/s02a 全是 TEXT，去重容量逻辑/统计都靠运行时 `float()` 解析，脏值静默变 None。

**建议**：

1. 在 s01b 入库前用一个 `_parse_number()` 把"约50""50-60MW""1,200"等清洗为 `REAL`（范围值取中位或区间两列），并保留原文到 `*_raw` 文本列以备追溯。
2. s02a / s03 对应列改 REAL。
3. 新增 `capacity_source`（原文/反推/人工）配合 §A.3。
4. 一次性迁移脚本：把现有 TEXT 容量批量清洗为数值（参考 `scripts/clean_historical_data.py` 的写法）。

### C.2 储能容量独立字段（数据筛选 #9）

**现状**：综合能源项目把"PV 100MW, BESS 50MW"塞进 `capacity_details` 自由文本，无法统计储能。

**建议**：在 `project_events`（及 s01b extracted_projects、s03 projects_flat）新增：

- `storage_power_mw REAL`（储能功率）
- `storage_energy_mwh REAL`（储能容量，度电）
- 发电类容量仍用 `capacity_mw`。
  prompt（§A.4）同步输出这三个值。s04 可据此新增"储能"专门视图。

### C.3 项目编号按时间排序（数据筛选 #11）

**现状**：`_gen_canonical_id`（s02a L187-194）= 现有最大号 +1，**按入库顺序**，导致"最新项目编号最小/新增似乎要重排"。且字符串排序在 >9999 后出错。

**关键权衡**：ID 是 `canonical_projects` 主键，且被 `project_events.canonical_id`、s03、s04、已发布链接、你手动修过的记录引用。**不能轻易整体重排**（会破坏所有外链与历史引用）。

**建议（二选一）**：

- **方案 1（推荐，低风险）**：ID 保持"稳定、与时间无关的流水号"角色，**不再追求编号=时间序**；另外新增 `display_order`（按项目最早事件日期排序的展示序号）专供前端/导出排序与展示。这样既不破坏主键稳定性，又满足"老项目在前"的呈现需求。
- **方案 2（高风险，仅在你确实要"编号即时间序"时）**：做一次性"冻结重排"：按各项目最早事件日期重排 `-NNNN`，同步级联更新所有 event_id 与所有引用，并保留 `old_id → new_id` 映射表给历史链接做重定向。此后新增项目只能继续往后排（无法保证插入到中间仍有序，除非每次重排）——所以本质上还是回到方案 1 的展示序思路更可持续。

同时修复排序 bug：`ORDER BY id DESC` 改为按数字段排序（`CAST(substr(id, ...) AS INTEGER)`），避免超过 9999/99 后进位错乱。

### C.4 时间点精确到月 + 单项目时间线（数据呈现 #3、#1）

见 §D.1（与时间建模强相关，统一在 D 类说明）。schema 侧需要：`project_events` 保证每个里程碑事件都带 `event_date`（YYYY-MM-DD，至少到月），s03 不再只导出"终态年份"。

### C.5 链接字段（数据筛选 #7 衍生）

你已手动修完那批错误链接。结构上建议：official/non-official 链接已是 JSON 数组（s02a schema L117-118），保持即可；但 s01b prompt 明确不填链接（L518），链接全靠 external-tools 后补——建议把"链接补充"也纳入主流程或定期任务，减少手动修正。

## D 类：时间维度建模与数据呈现（数据呈现 #1~#4）

> 这是你最在意、影响最大的一类：**"2024 签约、2026 竣工的项目被算成 2026，导致早期年份项目越来越少"**。

### D.1 从"项目级终态"改为"事件级时间线"建模（数据呈现 #1，核心）

**现状根因**：`s03/flat_builder.py`（L232-296）把一项目压成一行，代表行取**阶段优先级最高**的事件，`event_year` = 该事件年份；`stats_builder.py` 所有聚合都按这个单一 `event_year`。于是每个项目在时间趋势里**只在它的终态年出现一次**。

**建议**：

新增**事件级聚合表** `stats_timeline_events`：

- 维度 `year × month × category × stage`，**一个项目在它经历的每个阶段-年份都各计一次**。
- 这样"2024 签约 + 2026 竣工"会同时出现在 2024 的"签约"和 2026 的"竣工"里，时间趋势图真实反映各年活跃度，早期年份不再被掏空。
- 现有 `stats_timeline`（按终态）可保留作为"项目当前状态分布"用途，但**时间趋势图改用事件级表**。

**注意**：这会改变前端图表语义（从"项目数"变成"里程碑数"），需要在 UI 上说明口径（如分 tab："新签约""新开工""新投运"）。

### D.2 统计到月份（数据呈现 #3）

`flat_builder.py` 已有 `event_month`（L367），但 stats 表只用 year。配合 D.1 第 2 步，把月份纳入事件级聚合维度即可。单项目详情页则展示完整 `signed/start/completion` 时间点。

### D.3 移除 "project count"（数据呈现 #2）

你认为不必放 project count。这是纯前端展示决策：在 s04 的图表/指标卡里去掉"项目计数"展示项（或改为更有意义的指标，如装机容量合计、按里程碑的活跃度）。属小改动，前端 `MapPage.tsx` / 图表组件层面处理。

### D.4 UI 参考 Cobalt & Copper（数据呈现 #4）

参考 https://cobalt.chinaglobalsouth.com/ 做一次 s04 的信息架构对标。建议单列一个 UI 重构需求清单（与 F 类的"前后端划分"一起规划），本文件先记锚点，不展开细节。

## E 类：复核机制与外部交叉验证

> 目标：把"AI 一次性提取"升级为"提取 + 多源复核"，对应你"验证结构需要重新设计"。

### E.1 复核 agent 化（与 A.0 合并设计）

把"复核"做成 A.0 里 Agent 5（自检）+ 专门的"复核 agent"：对低置信字段（容量、金融、签约日期）触发二次核验，而不是一次提取定终身。现有 `s02c_cross_verification` 的"向量匹配 + LLM 确认"框架可改造复用（其 GDELT 数据源已失效，需换源，见 E.3）。

### E.2 未点名中企的复核流程（数据筛选 #1）

**现状**：空实体一律 → "Unknown"，丢失"已知有中企、只是没点名"的信息。

**建议**：

- prompt 输出区分两种情况：`no_chinese`（确无中企）vs `chinese_unnamed`（明确有中企合作但未具名）。
- 后者 `implementing_entity` 填 `"某中国企业"`（而非 Unknown），并置 `needs_manual_review=1`（s02a 已有该字段，L127），进入人工复核清单。
- s03/s04 对"某中国企业"做特殊展示（提示待核实）。

### E.3 外部信源交叉验证换源（数据筛选 #4、#10）

- GDELT 失效（s02c 文档已记），需换源。**上市公司**（你 #4）：可针对上市中企，接入证券交易所公告/巨潮资讯/公司 IR 页面作为高可信投融资源。

## F 类：架构扩展性与自动化运行（扩展性 #1、#2）

> 面向 v2 → v3 的大版本，建议在前述数据问题稳定后再启动。

### F.1 多领域扩展（可再生能源制造业 / 矿产 / 政策库）

**建议架构**：

- **抽象出"领域(domain)"维度**：canonical_projects 增 `domain` 字段（renewable_energy / re_manufacturing / mining / policy…）。提取侧用"领域分类 agent"先判定领域，再路由到该领域专属的抽取 prompt/schema。
- **pipeline 选型**：建议"一条主 pipeline + 领域插件"而非完全独立的多 pipeline——共享爬虫、去重、实体归一、导出等通用环节，只让"分类规则 + 字段 schema"按领域可插拔。这样维护成本最低，也符合你"保持扩展性"的诉求。
- 政策库与项目库 schema 差异大，可作为独立表 + 独立 prompt，但共用实体归一化与前端框架。

### F.2 清晰的前后端划分与自动运行（扩展性 #2）

**现状**：s04 是纯前端 fetch 静态 JSON，s03 手动 `uv run run_export` 生成；时间是手动改的。

**建议演进路径**：

1. **近期（保持纯前端，先自动化数据生产）**：把 s01a→s03 整条 pipeline 做成定时任务（cron / GitHub Actions），自动产出并提交 JSON，s04 自动部署。无需后端即可实现"自动运行"。
2. **中期（需要交互式查询/写入时再上后端）**：若未来要在线编辑、人工复核、按需查询大数据，再引入轻量后端（FastAPI + 现有 SQLite/Postgres）提供 API，前端从 fetch 静态 JSON 改为调 API。
3. **配置单一可信源**（与 check-record §四 #3 呼应）：把所有枚举的中英文映射、隐藏/无容量类别清单收敛到**一份配置文件**（如根目录 `enums_mapping.json` 已存在，应让 s01b/s02a/s03/s04 都从它读取或由它生成各端常量），杜绝"四处硬编码、改一处漏三处"。这是支撑多领域扩展的前提。
