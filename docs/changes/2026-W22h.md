## 附4：C1 单批试跑暴露的两个 blocker + 修复

单批试跑（`2024-01-01_2024-01-31`，252 篇，内层 24）暴露两个会让全量跑挂的问题，均已修（纯错误处理/编码，不改提取/prompt/schema 逻辑）：

- **Blocker 1 · GBK 编码崩溃**：worker `print()` 中文标题，Windows 控制台默认 GBK，遇非 GBK 字符抛 `UnicodeEncodeError` 杀掉 worker 线程 → 整批中断。**修**：`main._setup_run_logging()` 强制 `stdout/stderr` UTF-8（`errors=replace`）。
- **Blocker 2 · 单篇异常拖垮整批**：`_process_article` 仅 `except RuntimeError` 且只包住 `extract_one`，后处理段（建 row/实体循环等）的任何其它异常会逃出 `executor.map` → 整批 252 篇全废、0 行入库。**修（Design 1）**：新增 `_process_article_safe` 包装——单篇任何异常只 `logger.error`（含 link/title/traceback）+ 计数，**不落任何表**；失败篇因此不进去重集（`already_processed` = extracted ∪ no_chinese ∪ discarded），**重跑 `run_bulk_extract` 自动只补跑失败篇**（成功篇被去重跳过、不重复花钱）。
- 试跑同时验证提取链逻辑工作正常（S1 门 / S2 / S34 合并 / 母子公司归一 / EN 缓存 / S5 均运行，verdict 合理）；日志中的 503/JSONDecodeError/枚举校验失败均 `attempt=1/3` 重试后自愈，非崩溃主因。

## 附6：容量单位 bug 修复（P prompt + D 确定性兜底/清洗）

C1 全量 guardrail 抓到 56 行 `capacity_mw≥50000`（最高 7,000,000 MW）。**根因（已核）**：非 `bri_parse` bug——bri_parse 忠实解析了 LLM 给的数字；是 **LLM 把中文「万千瓦/千瓦」换算到 kW 却倾进了 `Capacity (MW)` 字段**（如「600万千瓦」=6000MW 填成 6000000）。影响 bounded：7203 有容量行中 190 行按千瓦口径、其中大多换算正确，仅 ≥50000 的 56 行 + 阈值下 ~1 例错；`>50000` 守卫网住了 egregious 的。

- **P（S2 prompt，`prompts/s2_basic.py`）**：`Capacity (MW)` 字段加换算规则「一律 MW：万千瓦×10、千瓦÷1000、GW×1000」+「关键规则」补一条带例子（600万千瓦=6000 不是 6000000）。名称仍保留原文单位。仅动容量字段，不跑 eval。
- **D-forward（`tools/project_extractor_tool.py`）**：新增 `_normalize_capacity_mw`——`capacity_mw≥50000`（物理不可能，单站最大三峡 ~22500MW）÷1000 还原为 MW；写库前包住 `bri_parse.parse_number(cap_raw)`。`capacity_mw_raw` 原文保留不动。
- **D-cleanup（现有库）**：对 C1 产出的 `projects.db` 跑一次性 `UPDATE … SET capacity_mw=capacity_mw/1000 WHERE capacity_mw>=50000`（先 `.bak_20260602_235452` 备份），**56→0**；抽样 7000000→7000、6000000→6000，raw 原文保留。
- 新增 `tests/test_capacity_normalize.py`（4 测试）；s01b 全测试 **169 passed**。
- 取舍：÷1000 对「kW 倾入」是对的；个别非此错法的可能不准，但 ≥50000MW 本就非法、÷1000 后落回合理区间，且 C2 review 可再核。
